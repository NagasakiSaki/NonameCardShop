## 查询

| 名称 | 输入 | 返回与用途 |
| --- | --- | --- |
| `management.insights` | `{day?:正整数}` | `ManagementInsights`。默认今天，历史日只返回当时已观测数据，不拼今天的库存/顾客 |
| `experience.guide` | `{}` | `ExperienceGuide`。各步骤、真实进度、可选项、下一步和跳过状态 |
| `experience.events` | `{}` | `ExperienceEvents`。真实可参赛顾客、可安排性、原因和活动历史 |
| `experience.stories` | `{limit?:1～100的整数}` | `{items:ExperienceStory[]}`，默认最新 20 条，倒序，带实际来源事件 ID |

以上使用现有 `{ok,revision,data}` / `{ok:false,error}`，查询不修改世界、随机源、现金和存档。未知历史日返回 `NOT_FOUND`，不要当成零流失/零成交。

`shop.snapshot` / `snapshotUpdated` 新增轻量 `experience:ExperienceSnapshot|null`，含覆盖程度、是否跳过引导、到访/离店数、最近记录 ID、当日活动状态。不要每一帧重查全部经营数据；完整手账打开时查询，HUD 按相关状态变化刷新。读档收到 `worldReset` 后清理旧结果和缓存。

角色还带 `customerCategory`，当前访问带 `visit.intent`。可以用它展示“姓名＋类别”和简短意图；类别来自熟客类型/行为，不由人物贴图决定。旧访问可能缺这些字段，显示“顾客”和当前 activity，不自行推断预算。

## 命令

所有命令走原有 `host.command`，使用稳定 requestId 和分支幂等检查，不直接改对象。

```js
await host.command({
  requestId: 'stable-request-id',
  type: 'experience.setGuideSkipped',
  payload: { skipped: true },
});

await host.command({
  requestId: 'another-stable-request-id',
  type: 'experience.scheduleEvent',
  payload: { eventId: 'community-intro' },
});
```

- 引导开关只影响展示意愿，不锁功能、不推进任务、不另发奖励；新档默认开启，旧档迁入默认跳过，可重新开启。
- 活动安排返回 `{event}`。第三天起，准备/营业阶段可安排；需要开启 NPC 模拟与自动比赛，且有两位钱包足够、未参加其他牌局、持有实际可参赛流通卡的顾客。
- 不可安排返回 `EVENT_UNAVAILABLE`，`error.details` 是原因数组，例如 `NOT_ENOUGH_PLAYERS`；UI 显示原因，不用假 NPC 补数。
- 一天最多安排一次。重复同 requestId 返回原结果，新 ID 重复安排被拒绝；编辑配置换活动 ID 也不能绕过当天上限。具体活动 ID 从查询 proposal 读取，不在界面写死。
- 邀请只提高真实顾客的到访优先级，并让牌桌优先配对；仍需正常入店和走到座位，不瞬移、不创建钱或卡、不绕过冷却/站位。
- 达到该次活动冻结的场数后为 `completed`；打烊仍未完成为 `ended`，不伪造胜负。日初读档恢复安排前状态，精确时刻备份恢复实际进度。
- 活动面板通过现有窗口申请暂停。关窗恢复后比赛才推进，页面不用自己的现实时间倒计时结算。

## 统计口径

`visits.departed` 等于五种 `outcomes` 之和；每次有记录的访问只归一种结果，按以下优先级：

1. `purchased`：有购物行为；即使也参赛/捡牌，仍只计一次。
2. `played`：没有购物但完成过 NPC 后台比赛。
3. `scavenged`：没有购物/完赛但捡到了牌。
4. `interrupted`：没有上述行为，因路径/设施技术问题离场。
5. `unconverted`：其余未成交访问。

`unconvertedReasons` 对每位最终未成交访问只给一个原因，合计等于 unconverted。预算、价格等以最后一次实际反馈为依据；打烊中止标“营业结束”。技术中断单列，不能计入玩家经营失败或扣声望。

`issueVisits` 是“访问×原因”去重，同一人反复找不到商品不重复累计相同原因，但可能先缺货、后预算不足，因此总数可以大于未成交人数。成交者也可能遇到满桌，它不是未成交分母。

已接入的观察点包含缺货、预算/价格拒绝、访问超时的最终原因、无空桌及技术离场；并非每个原因都有即时场景动画。C 不能虚构排队系统已经具备的新能力。历史旧访问无 visitId 时不倒造到访数。

`coverage='complete'` 表示从新日初完整观察；旧档当天迁入标 `partial`，只统计迁入之后。下一日重新完整观察。独立持久计数不依赖最近 1000 条日志，因此日志滚动不会清零日报。保留天数随世界 maxDays，最多 120 天；超过范围或旧版本没有的数据返回 NOT_FOUND。

## 商品、财务与建议

- products 的 `kind` 为实物单位 pack/box。sold、warehouse、onShelf、inTransit 都按该单位计数，不能将一盒既算一盒又加 24 包。
- 今天包含当前商品与实际持有/在途商品，即使没有销量也可显示。历史只保留实际观察到的售卖/缺货行，不返回今天的库存和新价格。
- warehouse 包含仓库实物；availableWarehouse 才排除保护与占用。页面不可把所有仓库物品都当可上架。
- referenceWholesale 是当前供货参考，不是可直接成交的报价。下单仍走 supplier.basketQuote / products.quote。
- stockoutVisits 只有访问已明确意向商品却没买到时才归到该商品；空店且没有具体商品意向只计总体缺货，不给每个主题都加一次。
- cash.change 是可用现金差，debtChange 是欠款差，taskRewards 是当天奖励毛额，不能互相代替。cash.opening 是观察起点余额；partial 日不冒充真正 08:00 余额。
- 经营利润继续读 `ledger.daily.netProfit`，收入/成本也继续使用 ledger；不要根据 cash.change 反推利润。
- 新日结 report 冻结钱包和未售估值；读取历史 ledger 的 `walletAsOf` / `valuationAsOf` 为 `day-close`。旧 report 没快照时保留兼容返回，但标 `current-fallback`，不能当当日值展示。
- suggestions 是依据实际缺货/预算/桌位记录生成的有限建议，并附 evidence；不承诺最优收益，不自动采购或改价。

## 本店记录

当前支持：他人弃卡被拾回、拾回的实物卡实际出现在胜方出场阵容、交流会完成。保留 sourceEventId、inventoryRef、matchId 与 simulated。

模拟胜利明确标“模拟比赛”；胜方携带某卡不等于证明由此卡造成胜利。KOF 仅检查实际出场部分，未上场的替补不生成获胜故事。查询与读档不重新随机生成消息，不向不存在的卡补来源。

## 编辑入口与前后端分工

默认内容在 `data/shop-experience.mjs`；当前档案配置在 `config.list` 的 `backend-experience`。可用现有 `config.validate` / `config.apply` 编辑引导、定位点、条件、故事容量与活动文案/最低日/目标场数，`config.restoreDefault` 恢复该配置默认值，不删除当前进度或已安排的活动。

支持的 goal 指标：ordered、received、opened、sales、marketSales、shelved、daysClosed、regularTalks、upgrades、communityEvents。新增指标要先写后端采集与验证，不能只加字符串期待自动生效。

已经安排的活动保存自己的参与者和目标，之后改默认配置不改变这次活动。新配置不额外发放奖励，当前高额自动任务继续由 tasks 模块负责。

- B：沿用交易接口，可展示 insights 的库存与参考档位，不接管资金逻辑。
- C：使用本页查询/快照，按正确分母展示日报与顾客状态；自己的独立预览继续用相同形状的 Mock。
- A：仍只管素材与状态外观，导航和实际占位由主模型接入。
- 主模型：真实接口绑定、窗口暂停、保存恢复、事件与账目。其他模型不因此修改正式 contracts/backend 或提前安装候选。
