# 对战房间与四模式评分

更新：2026-10-26。适用于当前开发版，接续 V7 经营挑战与赛制接入。未更新 EXE。

## 已确定的规则

武将全局分、当前稀有度和供货强度均使用四种模式的等权平均：

```text
斗地主分 = (地主身份分 + 农民身份分) / 2
武将全局分 = (BO3分 + KOF分 + 斗地主分 + 2v2分) / 4
主题强度 = 该主题全部武将的全局分的算术平均
```

不按模式热度加权，不按卡盒出货概率加权，不把斗地主的两个身份当成第五种模式。评分保留三位小数，主题展示保留两位；价格档选择使用策略中的主题平均值。明确被当前原生兼容名单禁用的模式记 0 分，固定四项分母，同时禁止该模式选将；能力未完整认证不等于已经禁用。

当前稀有度界线：N <57，R ≥57，SR ≥65，SSR ≥78。稀有度由全局分产生；已经印刷的卡保留原印刷稀有度。全目录 2563 名武将，当前分布 N1773 / R469 / SR284 / SSR37，相比旧两模式模型有 119 名改变当前稀有度。目录包括停产主题，正常供货只包含 16 个主题。

## 评分依据和适用范围

三国杀没有本项目可直接采用的、跨这四个自定义赛制的官方统一强度公式。本模型是可解释的资源收益估算，不是官方排名或实测胜率。

- [Wizards：Tempo and Card Advantage](https://magic.wizards.com/en/news/feature/tempo-card-advantage-delicate-balance-2014-11-17) 讨论牌差、节奏及其随局势变化的价值，支持将不同资源拆开核算，而不是只按技能数量打分。
- [三国杀官方 FAQ](https://www.sanguosha.com/faq.html) 可作为团队配合、分模式分析的参考。实际规则以本项目固定的无名杀 1.11.6 profile 和模式适配为准，不复制其他产品的赛季数值或规则。

“1 血约 2 牌”、场景窗口、触发概率和评分权重均为本项目的调参假设，不能称为上述来源给出的标准。缺少实战样本时，置信度只表示模型审核程度，不是胜率或统计置信区间。

每个身份以空白四血武将为 50 分基线，核算有效补牌、伤害、防伤、回复、控制和牌质，扣弃牌、交牌与掉血代价：

| 资源 | 每单位分值 |
| --- | ---: |
| 净牌收益 | +10 |
| 有效伤害 / 防伤 / 回复 | 各 +20 |
| 控制 | +10 |
| 牌质改善 | +5 |
| 卡牌机会成本 | -10 |
| 主动掉血 | -20 |

额外体力以每点 5 分为基础，按场景窗口摊销，超过六血的部分不继续线性放大。每角色场景分限制在 0～200。KOF 使用较短窗口，换将重新摸四张，不增加旧手牌继承分；旧 burst 和 carry 项均不额外加分。地主基础增益已在该身份的空白基准内，不当作每名武将的额外技能收益。

| 场景 | 对手 / 队友 | 估算窗口 | 受击暴露系数 | 成长兑现系数 |
| --- | --- | ---: | ---: | ---: |
| BO3 | 1 / 0 | 4 | 1 | 1 |
| KOF | 1 / 0 | 3 | 1 | 0.75 |
| 地主 | 2 / 0 | 3 | 1.4 | 0.8 |
| 农民 | 1 / 1 | 4 | 0.85 | 1 |
| 2v2 | 2 / 1 | 4 | 1.2 | 1 |

未人工复核的技能只对明确的受伤触发、多人目标、他人回合、一次性收益和成长部分作有界调整，不能给所有技能直接乘人数。每轮限一次不因人数自动翻倍，单目标不给群体收益。给队友的资源和交给敌人的资源分别处理，互斥分支不能同时累计。

11 名重点武将有独立身份向量和中文解释：刘备、郭嘉、貂蝉、荀彧、华佗、孙尚香，以及族荀爽、族荀淑、族荀谌、族荀彧、吕蒙。其余仍保留估算标记，后续应优先复核极值、低置信度以及实战偏差大的武将。

示例：荀彧 BO3 55、KOF 52.333、斗地主 62.792、2v2 70，全局 60.031；刘备全局 54.5，团队给牌不能当作单挑免费牌差。

## 房间流程

1. 在报名台或牌桌选择模式、对手并创建房间。默认只允许店长有一个活跃房间，占一张空闲桌。
2. 对手入房即确定整场备战池：BO3 1、KOF 3、斗地主 5、2v2 8 名不同武将。普通 NPC 必须实际持有且已流通，冻结实体副本及桌费预留。
3. 店长确认前可打开独立的双方备战池窗口，翻页看卡面、技能、本模式分和全局均分。该窗口只读，不修改对方名单。高手借用池同样公开，但不是可交易库存；取消重建高手房间不会重抽名单。
4. 店长跨页选满我方备战名单，再一次确认。确认在同一个世界事务中将房间预留转为正式比赛占用及桌费托管；失败完整回滚，不能只释放一半。
5. 逐局选将、真实引擎挂载、队友接管和整场可信结算沿用 V7。整场结束自动释放；中途退出依旧通过取消、认输、放弃等正式比赛接口处理。

没有合适对手时保留等候房间，关窗可继续经营，有合格 NPC 到店会自动入房。窗口交互本身暂停时间，关窗后的等候不暂停；默认等待上限 180 游戏分钟，当天 20:00 提前截止，打烊也会释放未开赛房间。正式玩家对局继续冻结时间，整场结算统一推进 30 分钟；NPC 后台对局不暂停。

旧存档已有比赛不强行重建，查询生成只读兼容房间；NPC 后台对局也以只读条目显示双方名单。当前房间是本地店铺的约战编排，不是联网大厅。

## 模块和接口

| 文件 | 唯一职责 / 编辑入口 |
| --- | --- |
| `data/strength-modes.json` | 场景参数、身份校准向量与说明；不放交易或 UI |
| `modules/backend/strength-modes.mjs` | 四模式评分、等权汇总、迁移和配置验证 |
| `data/backend-rules.json` | 资源权重、稀有度界线、四项各 0.25 权重、等待期限和默认价格 |
| `modules/backend/catalog.mjs` | 单卡评分、当前稀有度、版本指纹与公开 DTO |
| `modules/backend/room-state.mjs` | `world.combatRooms.version=1` 初始化、状态和世界一致性校验 |
| `modules/backend/battle-rooms.mjs` | 房间命令、锁定、NPC 绑定、查询与到期清理 |
| `modules/backend/operations-v7.mjs` | 房间对手计划、系列赛与现有可信结算的交接 |
| `modules/backend/runtime.mjs` | 命令队列、世界 fork、存档提交、加载与时钟；上述模块不私自写存档 |
| `frontend/combat/v7-room.mjs` | 房间与选将窗口；不自行冻结名单或扣费 |
| `frontend/combat/room-pools.mjs` | 双方名单查看与翻页；不提交对方选将 |

查询：

```js
query('combat.rooms') // {version, items, active}
query('combat.room', {roomId}) // RoomView；纯读，不消耗随机数
```

命令通过既有 `requestId` 幂等队列提交：

```js
command({requestId, type:'combat.room.create', payload:{formatId, opponentId?, tableId?}})
command({requestId, type:'combat.room.prepare', payload:{roomId, reserveRefs, proof, expectedRevision?}})
command({requestId, type:'combat.room.cancel', payload:{roomId, proof, expectedRevision?}})
```

`proof` 必须来自最新 RoomView：`{worldId, branchId, resourceRevision}`。读档、换分支或房间已更新时旧操作被拒绝；前端重新查询后确认。`expectedRevision` 可省略，缺省使用 proof.resourceRevision。创建房间没有旧房间 proof，但仍校验世界、营业、桌位、距离和唯一活跃房间。

RoomView 包括 roomId、roomLabel、revision、proof、formatId、status、opponentId/name、tableFee、expiresAt、capacity、pools.mine/enemy、readiness、matchId、series。expiresAt 是 `day×1440+minute` 的游戏绝对分钟。公开池含 generalId、cardKey、imageUrl、rarity、globalScore、modeScores、loan，不暴露普通 NPC 实体副本引用。兼容条目 `roomId='match:'+matchId` 标记 legacy，只读。

卡牌 DTO 新增 `power.modeScores`、`power.roles`、`power.modeAvailability`、`power.aggregation`。角色 vector/contributions 是该角色估算，顶层 vector 保留旧接口参考，顶层 contributions 为四模式平均贡献。未来新模式必须显式扩展版本、汇总口径、能力检查、查询和测试，不能静默改变当前四项分母。

## 存档和维护

- `resource-yield-1` 旧评分在加载时迁移为 `resource-four-mode-2`，标记 ratingRulesVersion。已经迁移过的不重复覆盖自定义规则；未知未来方法不作降级迁移。
- 迁移刷新供货目录及后续新报价；已制造包盒的完整内容、印刷稀有度、实体成本、已建订单和手工价格保留。旧日档加载后也走同一迁移入口。
- 保存整个 combatRooms；恢复分支时更新房间 proof，并与表位、NPC、费用预留、实体锁一起恢复。未知未来房间 namespace 保留，当前客户端不执行对应命令。
- 引擎升级继续走 `integration/modes/` 的版本 profile、能力探测和原生禁用清单，房间不直接依赖引擎内部事件。不得把当前四模式估算当作全技能认证。
- 修改评分后运行 `npm run strength:report` 生成可审计全量报告；模型指纹包含场景策略、旧校准和原生兼容名单，防止报价沿用过期模型。
- 本轮定向回归：`npm run test:rooms`。真实引擎测试使用受控胜负夹具验证接入和结算，不证明难度、AI 胜率或经济长期平衡；这些仍需试玩和实战样本。
