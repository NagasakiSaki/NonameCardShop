日期：2026-10-24。状态：**设计与交接稿，尚未实施**。

适用工程：`D:\GameDev\NonameCardShop`。核对基线：本地 `641d8a7f`，对应私有发布历史 `95a99586`。现行业务契约为 `card-shop-ui/1.0`。

本轮只编写本文件。下文的目录、CLI、`card-shop-ui/2.0` 和新增业务接口均为后续开发目标，不代表当前已经存在。执行实现任务应以用户之后的指令为准。

## 1. 本次确定的方向

用户已认可 `experiments/character-art/` 中的**行走表现**，下一版保留这种效果。采用“俯视卡店自由走动＋独立头像＋以卡面为主的交易界面”。试验页的 B 方案只保留为比较记录，不把游戏改成取消行走的纯经营仪表盘。

前端的页面结构、组件和交互重新设计；已有权威经营规则、实物库存、存档、评分、卡包配盒、市场流通和原无名杀引擎继续复用。把视觉与交互重建和业务规则重写分开安排。

### 1.1 必须落实的用户要求

1. 使用本次认可的行走小人比例、四向侧面和八帧步态，保留斜向移动、滑墙、点击寻路、无缝换房。
2. 人物工具要让其他模型也能通过配置、命令行和普通文件操作，不依赖当前对话、特定模型或必须点击的 GUI。
3. 恢复旧版直观的卡面展示和快速操作，买卡、卖卡、收藏、开包、垃圾桶、组队等页面都应直接看到卡牌。
4. 进货和收货以商品、数量、价格、到货状态为中心，减少重复说明和长页面。
5. 重建整体设计语言和前后端展示契约，形成可交给另一模型独立开发的规范。
6. 本阶段不重建 exe，不清空或迁移玩家进度，不直接用演示数据替换正式世界。

认可范围要准确：用户明确确认了行走效果；试验头像的每套服装、发型以及全部 UI 细节尚未成为不可修改的定稿。头像和地图人物仍需统一外观。

### 1.2 一句话体验目标

玩家走进自己的卡店，看到有人挑包、拆包、捡牌和打牌；打开柜台后，像翻商品图册和整理实体卡册一样完成交易。

## 2. 当前问题与需要恢复的优点

以下是本次代码核查，和仅凭截图推断的问题分开记录。

| 当前事实 | 对体验的影响 | 重建要求 |
| --- | --- | --- |
| `frontend/ui/supplier.mjs` 给每个主题竖排显示产品版本、评分版本、价格版本、卡种分布、盒配额、每包均值、概率、保底等 | 每件商品占很长篇幅，下单信息不集中，跨商品比较困难 | 首屏商品图＋进价＋建议售价＋库存；详细规则进入商品详情 |
| 当前询价在各商品内部展开，再插入第二块报价表 | 报价位置随滚动变化，操作后跳到另一页，难连续采购 | 常驻购物篮，统一结算区域，确认后保留目录筛选与位置 |
| 二级市场买卡主列表是文字表格，第一列主要显示名称与稀有度 | 玩家无法直接凭画面辨认想买的卡 | 默认卡面网格；表格仅作为可选紧凑视图 |
| 卡面在部分收藏与详情中存在，但购买、收货、零售等页面没有统一图像入口 | 同一张卡或同一商品在不同流程像不同对象 | 共用 CardTile、ProductTile 和 ArtRef |
| 有分页查询，但部分页面只读一页，筛选刷新还可能重建整个面板 | 浏览大量内容时容易漏项、丢选择和丢滚动位置 | 统一分页、筛选、选择和恢复协议 |
| `imgWithFallback` 缺图时直接替换成普通“缺图”文字块 | 物品的形状、身份和操作入口容易一起丢失 | 固定外框占位图，保持卡名、稀有度、数量与操作 |
| 同一供应商面板混合订货、收货和物理零售货架 | 业务区域和页面导航互相跳转 | 采购台与收货台作为同一工作区，零售陈列作为独立工作区 |

旧版值得恢复的部分有明确源码依据：

- `app.js` 的图鉴以真实 `/img/…` 卡图、稀有度标识和 `×数量` 为主体，点击进入完整技能与大图。
- `styles.css` 将卡面按 3:4 展示，详情保留独立大图区域。
- `business-ui.js` 的供应商采用较集中的选择、数量和汇总表单，日常下单需要阅读的内容较少。
- `legacy.html` 用“供应商下单／收货仓库／库存开包”表达连续流程，经营摘要能提示当前最需要处理的事。

恢复这些优点，同时保留新版的权威报价、暂停、实物守恒和存档保障。旧版五档稀有度、旧单挑卡池、旧业务写入与不暂停的交互规则不随 UI 恢复。

## 4. 美术、像素和显示参数：硬性基线

这里区分四种单位：**源图像素、世界坐标、CSS 像素和设备像素**。不能将 64×64 的透明画布误解为人物身体必须填满 64 像素，也不能用设备 DPR 改变业务碰撞。

### 4.1 人物与地图

| 项目 | 规格 | 验收规则 |
| --- | --- | --- |
| 地图人物源帧 | **64×64 RGBA，透明底** | 采用已认可试验的比例，不回退到旧 96×128 参数人物模板 |
| 行走图集 | **512×256，8 列×4 行** | 每行 8 帧；行序 **上 0／左 1／下 2／右 3** |
| 步态 | 默认 **9 fps**，0→7 循环 | 仅移动时播放；停止后切指定待机帧，不原地踏步 |
| 落脚点 | 源帧 **(32,61)** | origin=(0.5,61/64)；换肤不改变脚底位置 |
| 可见人物内容 | 本次三套样例单帧约宽 **23～28 px**、高 **45～49 px** | 此范围是对试验素材的实测参考，不强迫所有发型裁成同一矩形 |
| 外观侧面 | 左／右侧面独立可识别；背面没有正面五官 | 禁止用“正面抹去眼睛”充当侧面；有不对称配饰时单独处理左右 |
| 行走方向 | 输入八方向、图像四朝向 | 归一化斜向速度；等幅斜向默认取横向朝向，与试验一致 |
| 逻辑地砖 | **16×16 世界单位** | 现有主店 30×20 格，即 480×320；对战房继续本地坐标＋世界偏移 |
| 地图源图细节 | 允许源瓦片 **32×32** 对应 16×16 逻辑格 | 清单明确 `sourceScale=2`，不要再给全部系统统一乘 2 |
| 角色碰撞 | 初始目标为脚底约 **12×8 世界单位**，由导航模块配置 | 禁止把整个 64×64 帧作为碰撞箱；实际可走性仍由 Host 决定 |
| 地图缩放 | 近邻采样，桌面优先 **2×**，可选 1×／3× | 不给人物单独设置 0.38、0.9 等非整数压缩来“塞进地图” |
| 绘制坐标 | 逻辑移动允许小数，最终绘制对齐像素 | 平滑移动时保持采样稳定，不能破坏斜向和滑墙 |
| 房间切换 | 同一连续场景 | 跨逻辑房间使用 Host 的边缘验证，不重启场景，不丢按键状态 |

角色比例与动画不能因“需要更多细节”而自行换成另一种全身模型。提高细节优先修改部件、轮廓和颜色，而非扩大人物在房间中的占地。

### 4.2 头像、卡牌与商品

| 资源 | 原生／展示规格 | 说明 |
| --- | --- | --- |
| 人物头像 | **96×96 原生**；常用展示 192×192，详情可 288×288 | 1×／2×／3×近邻放大；不得从行走图放大裁切生成 |
| 头像表情 | 首批中性、微笑、闭眼 3 种；对话需要时扩展 | 眼睛与嘴部表情应各自可配置，保持人物身份 |
| 单卡画框 | **3:4**；主网格卡面 144×192 CSS px，最低 128×171 | 武将原图保留原有细节，**不整体像素化** |
| 大图详情 | 常用 **300×400 CSS px** 以上 | `contain` 展示完整画稿；焦点裁切只使用经标注的数据 |
| 紧凑卡面 | 96×128 CSS px | 仅作为可选紧凑视图，不作为买卖页默认规格 |
| 卡图缓存 | 建议 288×384 缩略图＋原图 URL | 不把大图预加载到所有库存行；缺图仍保留物品身份与边框 |
| 卡包包装 | 64×96 原生像素图，展示 128×192 | 主题名、系列色、包数可识别；包装不是开包结果保证 |
| 卡盒包装 | 96×96 原生像素图，展示 192×192 | 与散包有明确形态差异，保留密封盒和拆盒来源标记 |
| UI 图标 | 16×16 或 24×24 原生，按整数倍展示 | 统一线宽和调色，常用入口必须同时有文字 |

原卡图、像素包装、地图小人和 HTML 中文字体采用各自合适的采样方式。禁止在页面根节点统一设置 `image-rendering:pixelated`，导致武将画稿和中文排版一起失真。

### 4.3 字体、界面与屏幕

- 桌面主要基准：**1366×768**；同时设计 1920×1080 与 1280×720。桌面常用中文正文 **16 px**，次要信息 14 px，极少量辅助信息最低 12 px。
- 人物头顶姓名约 **14 CSS px**，类别 12 px，屏幕尺寸稳定；始终显示姓名＋类别，额外行为文字只在必要时展开。拥挤时错位排布标签，不能直接让名字互相覆盖。
- 字体使用本地系统中文字体作为可用基线；像素字体只用于少量标题或装饰。替换字体须同时记录字体许可证和缺字回退。
- HUD 高 **48 px**；经营侧栏宽 **288 px**；常规间距 8／12／16／24／32 px；常用按钮高 36～40 px、触屏点击区至少 44×44 px。
- 1366×768 下地图目标保持 480×320 逻辑视口的 2×显示；1280 宽且放不下侧栏时，先收起侧栏为抽屉，再考虑缩小地图视口。禁止为了塞入更多按钮把所有 UI 字号一起缩小。
- 交易工作区参考宽 **1240 px**、最大高 `视口高−32 px`。1366 基准默认至少显示 **4 列×2 行**主卡面；1920 基准可扩大为 6 列。列表滚动不得同时带动标题和结算按钮消失。
- 卡牌详情参考宽 920～1040 px；左侧大图、右侧技能与操作。窗口小于 900 px 时改成上下布局，按钮仍保持固定可见。
- 420 px 窄屏为辅助适配：两列卡面、底部结算栏、单页抽屉详情，无页面横向溢出。首轮不因此改坏桌面主体验。
- DPR 只提高 Canvas 清晰度；不会修改帧尺寸、角色速度、碰撞或地图坐标。缩放按 [Phaser 官方 Scale Manager](https://docs.phaser.io/phaser/concepts/scale-manager) 的职责分层设计。

### 4.4 颜色与视觉层级

起始设计令牌：背景 `#141a1c`，面板 `#1d2528`，分隔 `#354143`，正文 `#f2ede0`，次要文字 `#a5b2ac`，鼠尾草绿 `#acd3b3`，旧金 `#e4bb7a`。最终可微调，但整套页面统一。

稀有度建议：N 石灰／浅灰、R 蓝青、SR 紫、SSR 旧金。必须同时写 N/R/SR/SSR，不只靠颜色。选中态用绿色边框和勾选，不能与 SSR 金框混淆。减少运动模式下停止闪光、翻牌摆动和扫光，交易反馈仍保留。

## 5. 总体界面结构

### 5.1 店铺主画面

地图是主体，右侧为可收起的店长手账；顶部只放当天时间、营业状态、资金、暂停与速度。背包、采购、市场、对战、任务、存档和设置通过清晰的菜单或快捷键进入，避免全部挤成一排小按钮。

手账默认只显示：今日营业额／目标、在途／待收货、货架补货提醒、最近一项可完成任务。点击卡片直接进入相应工作区，不先打开一层通用菜单。

NPC 保留真实阶段：挑选、排队、结账、拆包、弃牌、拾取、入座。头像展示发生在对话与人物卡中；地图始终显示完整行走小人。

### 5.2 统一的“卡桌工作区”

```text
┌ 页面标题 / 当前模式 / 返回 / 关闭 ─────────────────────────┐
│ 搜索、稀有度、主题、排序、筛选条件摘要                     │
├ 筛选栏 ┬ 商品图册 / 卡面网格 ────────────┬ 当前选择 / 购物篮 ┤
│        │ 卡图  卡图  卡图  卡图          │ 大图或交易明细   │
│        │ ×3    ×1    ×8    ×2            │ 数量、单价、净额 │
│        │ 卡图  卡图  卡图  卡图          │ 保护/占用说明    │
├────────┴───────────────────────────────┴──────────────────┤
│ 已选数量 / 合计 / 清空选择 / 主要动作 / 取消               │
└──────────────────────────────────────────────────────────┘
```

组件可以按页面裁减，但不能让所有卡片共用一长列说明文本。详情在当前工作区的侧栏展开，完整技能可进入一个覆盖层；返回后保留选中、购物篮、筛选和滚动。

### 5.3 导航和站位

- 查看目录、收藏、行情和牌桌状态允许远程打开，打开即暂停世界。
- 需要实体站位的动作：开包、密封零售上架、单卡交易、拾取垃圾、报名牌桌等，继续由 Host 校验。
- 站位不足时，在原工作区保留草稿，点击“前往柜台”后收起工作区、释放该窗口暂停、自动行走；到达后重新申请暂停并恢复原页。玩家取消寻路不会丢草稿。
- 禁止在持有“窗口暂停”的同时等待经营角色自动走到柜台。手动暂停等其他暂停原因继续保留，并明确提示为何尚未行走。
- 页面切换不引入第二层隐形旧窗口。最多一个主工作区＋一个详情覆盖层；确认和错误使用就地状态或轻量对话框。

## 6. 各页面的具体设计

### 6.1 采购：商品图册＋集中购物篮

入口是柜台和手账“采购”。目录默认显示在售的 19 个主题，不显示已停产七主题；旧库存仍从仓库查看。

每个商品格的首屏内容限定为：包装图、主题名、包／盒切换、当前进货单价、建议售价、仓库／在架／在途数量、加入购物篮。可附简短“每盒 24 包、每包 5 张”标记。包数、张数取 Host 数据，不在前端写死业务规则。

配比、散包概率、主题卡种、同档补位、版本历史和评分依据放在选中商品的详情抽屉。产品版本长字符串只出现在“更多信息”或诊断区，不占商品标题。

购物篮固定在右侧，支持多个主题和包／盒 SKU；调整数量无需重新展开商品。结算前显示货款、预计到货、可用资金、信用是否启用和实际应付。信用默认为关闭，不因不足款自动勾选。

点击“核对采购”时后台取得真实报价并在同一区域显示确认摘要；点击“确认采购”才提交。不要让玩家对每个商品先单独点“获取报价”，再到不同位置找确认按钮。报价期间允许浏览，修改数量会使旧报价失效。

采购成功显示订单号和到货状态，购物篮移除已成交项，目录停留在原位置。提供“查看在途”入口，不强制把整个工作区跳到收货页。

**多商品结算必须由后端整笔原子执行。** 不把 N 次单品下单循环伪装成购物车一次成交；批量接口未接通时，明确限制购物篮只能有一行。

### 6.2 收货：处理清单，而非订单说明书

分“待签收／在途／已完成”三个筛选；默认待签收。页头只显示待收几单、在途几单和下一笔预计到达时间。

每笔订单使用紧凑横向商品行：包装缩略图、主题、包／盒、数量、已付金额、到达状态、签收按钮。以“还有 12 分钟”或“已到货”表达时间；版本和原始订单数据可展开。

支持全选当前待收货和“一键签收全部已到货”；后端返回本次实际签收订单列表及入库数量，前端不能把在途订单误算为已签收。

签收后就地更新状态，提供“补货／开包／拆盒”快捷入口和“一直留在收货页”的选择。签收本身不自动拆包、不再次扣款、不改变旧盒内容。

### 6.3 密封仓库与货架

仓库中散包、完整盒、拆盒所得包清楚分组，均有包装图和实际数量。筛选“全部／可售／受保护／旧版库存”，箱盒来源与剩余包数可查看。

货架工作区左右呈现“仓库”和“在架”。点选数量后上架或撤回；支持补满货架、批量同价、恢复建议售价。容量以 Host 的货架单位为准，完整盒占用数也由 Host 返回。

普通密封零售区只出现包与盒；单卡上架放到二级市场。停产密封商品留在旧库存，不混入可补货列表，也不允许通过员工补货重新在售。

### 6.4 开包柜台

先看实际可开库存和包装；支持指定主题、数量、开本盒、所有可开包、是否包含完整盒。默认保留受保护与锁定实物。

确认前只展示将消耗几盒／几包、得到几张、剩余库存与排除原因。**不提前泄露密封包中的武将或稀有度结果。** 开包事务成功后才显示实际卡面。

单包默认五张大卡并排或扇形翻开；可跳过动画。批量默认卡面结果网格＋N/R/SR/SSR 汇总＋新卡／重复筛选，不逐包强制播放。大量结果分页或虚拟化，不能一次挂载几千个大图 DOM。

结果支持“保护新卡”“每个武将留一，其余上架”“只上架选中”“继续开包”。上架仍需经过市场柜台规则；前往柜台时保留本次结果与选择。

事务已成功后，关闭动画只停止展示，不撤回开包。刷新恢复实际操作结果，不重抽、不重复扣包、不把未播完动画当作失败。

### 6.5 收藏与卡册

默认卡面网格，显示名字、N/R/SR/SSR 和右下角 `×数量`；搜索、主题、稀有度、重复、可交易、保护和在售可组合筛选。提供未收集图鉴模式，但不要混淆“已知卡种”和“本世界已流通”。

首屏小卡只显示关键状态，选中后在侧栏展示总持有、可动用、受保护、在售、参赛占用。状态可能重叠，前端不能用这些数字简单相加减推导“可卖数量”。

默认按 cardKey 合并显示总量；不同印刷版可在详情展开，交易选择仍指向真实副本。印刷稀有度与当前全局强度不同时并列标注，不能直接改写旧卡的印刷记录。

“留一”默认以**同一武将 cardKey**为范围跨印刷版保留至少一张；受保护和参赛占用优先计为保留。需要按印刷版各留一时提供明确的高级选项。具体选择由后端预览决定。

### 6.6 二级市场：买卡和出售都先看卡

主模式为“买卡／出售收藏／我的挂单／街坊求购／成交记录”。不使用一个巨大的通用表格承担所有模式。

**买卡：** 卡面网格展示武将、实际可买数量、最低挂价、参考价与样本提示。点开某卡后在侧栏列出实际卖家和具体挂单；选择购买张数，Host 选择并报价真正可成交的副本。报价中可出现不同单价，必须明确展示。

**出售：** 直接展示自己可出售的卡面和数量，支持多选、数量、参考价倍率、单张价和批量应用。右侧显示“挂牌总额”与“成交后预计到账”，明确**上架即刻到账为 0**。不在普通挂牌中杜撰即时买家。

**我的挂单：** 保留卡面、价格、在售副本数量、改价和撤单；已售记录自动进入历史。价格修改也由权威事务处理，不能改完 UI 就算完成。

**街坊求购：** NPC 头像＋目标卡面＋需求数量＋实际收购价＋期限，已有实物时直接选择交付。不能把普通玩家挂牌和 NPC 已承诺收购混成同一种销售。

**价格详情：** 首层显示真实参考价、真实挂价、场次和胜率；无样本时写“暂无对战样本”，不造趋势线、百分比或热度。参考价、挂牌价、冻结买价和最后成交价分别命名。

市场刷新后保留选中卡种与滚动；具体挂单被买走时就地提示并刷新报价，禁止默默改买另一张不同价格的卡。

### 6.7 统一卡牌详情

左侧大图；右侧顶部为卡名、阵营、当前强度、印刷档位（有实物时）、价格与持有摘要。技能正文完整可读，多个技能有清楚分隔。技能源码在可展开的开发页，不默认占据玩家界面。

底部动作依上下文提供：购买、加入卖单、保护副本、加入阵容、丢弃。没有权限或不在站位时说明原因，并保留“前往柜台”入口。不要在收藏详情中展示一个必定报错、也不说明原因的“出售”按钮。

### 6.8 垃圾桶与人物互动

垃圾桶用卡面呈现弃牌，显示谁丢的、当天剩余保留期限、是否已流通。支持多选拾取和全捡，拾取由后端转移原实物，不克隆卡片。

NPC 对话侧栏使用独立头像、姓名、类别、活动与真实可交互项。角色外观不决定性格、预算、稀有度偏好或拾荒资格。名字＋类别继续常驻头顶。

### 6.9 对战、经营和存档

对战房以牌桌和座位为主，报名使用卡面阵容：BO3 一位、KOF 三位，有明确顺序。禁用原因由 Host 返回；继续使用实际持有、已流通的实物。`wagering=false` 时不开放赌注或抽水设置。

日报与经营页可以使用表格和简图，但不要把所有交易页一起改成后台报表。利润、营业额、采购现金流和未售估值分别展示。

存档按天、分支、时间点和预览摘要呈现；加载前展示将回到哪天、资金和收藏数量，保留备份与分支策略。前端重建不新建一个与旧档无关的本地收藏库。

## 7. 交易手感与状态规则

1. 所有交互工作区自动暂停经营；窗口关闭才释放自己的暂停令牌，不能解除玩家手动暂停或其他覆盖层暂停。
2. 信息浏览不增加“确认”步骤；付钱、消耗包、批量挂牌和批量丢弃才集中核对。批量不可逆结果要显示范围，不逐张弹确认。
3. 所有交易按钮在请求期间禁止重复提交；重试复用 requestId。界面先显示“处理中”，收到成功再改权威数量与资金。
4. 拖放可作为快捷方式，同时必须有点选＋按钮操作；不把拖动本身当作已成交。
5. 搜索与筛选本地状态持久到工作区关闭；异步结果带查询标识，旧响应不得覆盖新筛选。旧页请求可以取消或丢弃，不闪回第一屏。
6. 首屏加载先保留卡框骨架，图像加载失败有占位与重试。只请求名字、卡图、数量等必要字段，技能代码和全部副本按需加载。
7. 键盘可用：Esc 返回一层、B 收藏、E 交互；输入框和交易窗口打开时，不把按键送给世界移动。
8. 成功反馈集中显示结果与下一步；“已签收 3 单，新增 7 包”胜过一长串内部 ID。内部诊断写入开发面板。

## 8. 前后端边界与契约重设计

### 8.1 当前与拟定版本

- **现有可调用：** `contracts/card-shop-host.d.ts`、`contracts/README.md` 的 `card-shop-ui/1.0`。
- **拟新增：** `contracts/v2/` 内的 `card-shop-ui/2.0`。本文件仅给出草案；目前不得假设这些方法已实现。
- 传输维持 `connect/query/command/subscribe/pause/world/battle` 的 Host 形态，不强制改成 HTTP，也不因为业务在浏览器中运行就允许 UI 直接改世界对象。
- 2.0 主要重建展示 DTO、分页、批量报价与动作计划；评分、抽卡、价格、持有、流通、费用、时钟、存档和引擎结果只有一个权威来源。
- 前端开发使用类型明确的 Mock；正式入口只有 RealHost，后端缺能力要显式禁用。不能以演示模式混入正式存档。

### 8.2 公共响应、能力与标识

```ts
type Context = {
  contractVersion: 'card-shop-ui/2.0';
  worldId: string; branchId: string; revision: number;
};
type Page<T> = {
  items: T[]; total: number; nextCursor: string | null;
  queryKey: string; summary?: Record<string, unknown>;
};
type Response<T> =
  | { ok: true; context: Context; data: T }
  | { ok: false; context?: Context;
      error: {code: string; message: string; retryable: boolean; fieldErrors?: unknown} };
type CommandInput = {
  requestId: string; type: string; worldId: string; branchId: string;
  payload?: Record<string, unknown>; quoteId?: string; planId?: string;
};
```

连接返回 `capabilities`、金额单位、分页／批量限制、当前世界摘要、外观清单版本、图片版本与当前站位上下文。能力至少区分：批量采购、批量买卡、批量挂牌、改价、图集元数据、精确存读档与赌注。前端按能力显示功能，不用接口报错来猜能力。

requestId 的幂等边界继续绑定世界与分支。读档后旧分支成功回执不能被当成新成交。revision 用于同步与展示；是否使报价失效要看引用的价格、库存和分支，不要求任意 NPC 移动都使交易全部失效。

### 8.3 图像与卡牌的共享 DTO

```ts
type ArtRef = {
  assetId: string; originalUrl: string;
  thumbnailUrl?: string; aspectRatio: number;
  fit: 'contain' | 'cover'; focalPoint?: {x: number; y: number};
  status: 'available' | 'missing'; revision: string;
};
type CardBrief = {
  cardKey: string; name: string; generalId: string; themeId: string;
  art: ArtRef; currentRarity: 'N'|'R'|'SR'|'SSR'; globalScore: number;
};
type HoldingGroup = {
  groupId: string; card: CardBrief;
  counts: {owned: number; availableToSell: number; protected: number;
           listed: number; matchLocked: number};
  printings: Array<{printVersion: string; printedRarity: string; owned: number}>;
  referencePrice: {amount: number; version: string};
  actions: Array<{action: string; enabled: boolean; reason?: string; stationId?: string}>;
};
```

CardBrief 在收藏、买卡、求购、垃圾桶、开包结果和阵容中复用。所有这些视图从权威卡表关联同一 `art`，不让每页自己从中文名推断图片路径。

`status='missing'` 是明确数据状态。真实有图时不能把“没请求图片字段”伪装成缺图；有错图时不能随便拿另一位武将当替代。不同副本状态会重叠，counts 的权威含义由后端维护。

商品增加 `ProductBrief`：`productId, skuId, unit, themeId, name, packagingArt, cardsPerPack, packsPerBox, wholesale, suggestedRetail, stockSummary, availability, productVersion, priceVersion`。SKU 区分同主题散包与完整盒，旧版密封库存附独立印刷批次。

### 8.5 批量采购与买卡：先报价，再整笔提交

拟定查询 `commerce.quote`，输入 intent：`supplyPurchase` 或 `marketBuy`。

```json
{
  "intent": "supplyPurchase",
  "lines": [
    {"skuId": "standard:pack", "quantity": 3},
    {"skuId": "extra:box", "quantity": 1}
  ],
  "useSupplierCredit": false
}
```

返回：quoteId、各行真实单价和版本、数量、图片引用、货款、费用、现金应付、信用使用、预计到货、有效世界／分支与失效条件。单卡买入输入具体 listingId；按卡种购买多张时由 Host 在报价中明确解析出的每个 listingId 和价格，玩家确认的就是这份清单。

拟定命令 `commerce.commit({quoteId})`，附普通 requestId。一次事务中再次核对站位、资金、引用版本、在售状态和实物锁；全部成功才创建订单或转移卡牌并记账。任何一行失败整笔不执行，并返回可以定位到行的错误。不能靠前端回滚补救已经扣过的钱。

数量上限和可用批量能力由 bootstrap 发布。1.0 当前单笔商品数量上限为 20、单卡挂单为一张；新 UI 不自行突破，也不在后台静默拆成多笔。

### 8.6 非即时交易：动作计划与执行

拟定查询 `inventory.plan` 统一处理有副本筛选和批量结果的动作：`listSingles`、`listSurplus`、`shelveSealed`、`withdrawSealed`、`repriceListings`、`discardCards`。返回 planId、实际选中数量、保护／锁定排除、保留数量、影响范围、所需站位和失效原因。

拟定命令 `inventory.applyPlan({planId})` 原子执行。计划绑定真实副本与必要指纹；任何选择或保护变化都需重新校验。挂牌计划的显示字段应明确：`listingGross` 为挂牌总额、`immediateCredit=0`，不能复用买卡的 `totalDebit` 文案。

普通签收拟定 `stock.receive({orderIds})` 和 `stock.receiveAllArrived`；只处理真实 arrived 订单，返回成功入库清单。开包保留独立 `opening.preview/execute`：消费实物与结果存储是一笔事务，结果播放是纯前端。

这些是 2.0 目标。1.0 的 `inventory.surplusPreview`、`market.listSurplus`、`retail.listAll`、`supplier.receiveAll` 等仍作为兼容基础，不能因为改名而复制一套业务规则。

### 8.7 事件、暂停和长操作

事件保留 worldId、branchId、seq、revision；新增资源范围提示，例如 `changedScopes:['inventory','orders','wallet']`，前端只刷新相关查询。角色移动不触发整个交易工作区重建。

提供快照恢复与断线重连；读取日档收到 worldReset 时，清除旧 quoteId／planId／副本选择，更新地图与皮肤，保留可重新应用的非业务筛选。不能在新分支继续提交旧购物篮中的冻结引用。

开包等操作以 operationId/requestId 补查。浏览器超时不代表交易未执行；重新查询原操作后再决定重试。大批量结果按页读取，技能源码、全部实物副本与完整日志不混入首屏 DTO。

所有“模拟数据”“真实结果”“估计金额”“未验证能力”在界面和契约中分清。NPC 自动拆包、弃牌、拾取、参赛和结算继续在 Host 中推进，前端只根据活动阶段播放动画。

## 9. 让其他模型能操作的人物工具

### 9.1 现有能力与后续缺口

现有试验已经有 `appearance-data.mjs`、`portrait-kit.mjs`、`build-samples.mjs` 和许可证记录，可通过代码组合头像、改色和输出图集。现有批量脚本只构建固定预设，尚不是支持任意输入、稳定版本与完整校验的通用 CLI，也不是已安装的 MCP 插件。

下一阶段将其整理为独立工具包：**声明式 JSON 是入口，命令行是标准操作方式，可视编辑器和 MCP 是可选外壳。** 任何能编辑 JSON 和运行 Node 的模型都能使用，不能要求它先拥有当前对话的记忆或某个厂商图像 API。

### 9.2 工具与文件格式

| 工具 | 角色 | 是否必需 |
| --- | --- | --- |
| Node.js＋普通 ES modules | 配置读取、部件组合、校验、批量输出 | 是；沿用当前工程可运行版本 |
| PNG 编解码（当前试验 pngjs 7.0.0） | 读取现有部件、保留透明、写 PNG | 是；后续工具包独立锁定依赖，不靠隐藏的 `.local` 安装状态 |
| 当前 Canvas 预览器 | 即时换色、表情、四向预览与图集检查 | 是；使用同一配置和核心组合代码 |
| [LibreSprite 脚本接口](https://github.com/LibreSprite/LibreSprite/blob/master/SCRIPTING.md) | 手工修绘或 JavaScript 批处理桥接 | 可选；不能成为查看游戏的前置要求 |
| [Pixelorama 扩展系统](https://pixelorama.org/extension_system/extension_basics/) | 可视部件面板和修绘工具 | 可选；需要后续单独实现扩展，不宣称现在已有 |
| Aseprite | 已拥有时可用于专业修绘和导出 | 可选；不要求购买，工具许可证与素材许可证分别记录 |

### 9.3 拟定外观配置

```json
{
  "schemaVersion": "character-kit/1.0",
  "appearanceId": "shopkeeper-brown-01",
  "styleId": "lpc-revised-approved-01",
  "walk": {
    "bodyId": "feminine-thin-peach",
    "headId": "feminine-peach",
    "hairId": "bob-side-part-brown",
    "shirtId": "tshirt-forest",
    "pantsId": "pants-charcoal",
    "shoesId": "shoes-brown"
  },
  "portrait": {
    "baseId": "female01",
    "frontHairId": "female01",
    "backHairId": "short01",
    "clothesId": "female02",
    "eyesId": "female01",
    "expressionId": "neutral",
    "paletteId": "brown-sage"
  },
  "outputs": {"walk": true, "portrait": true, "contactSheet": true}
}
```

上述部件 ID 是拟定注册表名，实施时必须与真实来源一一映射。配置里不允许把任意 JavaScript／Lua 字符串当绘图内容执行。职业、钱包、性格、NPC 行为和卡牌能力不放进外观配置。

### 9.4 拟定 CLI 和输出

```powershell
# 以下为目标接口，当前尚未实现。
node tools/character-kit/cli.mjs list-parts --style lpc-revised-approved-01 --json
node tools/character-kit/cli.mjs validate --input data/appearances/shopkeeper-brown-01.json
node tools/character-kit/cli.mjs render --input data/appearances/shopkeeper-brown-01.json --out .local/art-review/shopkeeper-brown-01
node tools/character-kit/cli.mjs contact-sheet --input data/appearances --out .local/art-review/contact-sheet.png
```

每次输出 `walk.png`、`portrait-neutral.png`、其他指定表情、`atlas.json`、`appearance.json`、`credits.json`／`CREDITS.txt` 与四向接触图。stdout 输出结构化 JSON：成功状态、配置版本、源素材哈希、产物路径和验证问题；失败返回非零退出码，不只在图片上写一段错误文字。

atlas 必须包含 frameWidth=64、frameHeight=64、8 列、4 行、方向映射、fps=9、anchor=(32,61)、idleFrame（初始为 0，允许按朝向指定）、透明边界信息、sourceScale 和 assetVersion。游戏加载器读取元数据，不能继续假设旧版三列或旧版方向顺序。

校验至少包括：源部件存在、尺寸匹配、有效方向／帧数、alpha 不为空、脚底稳定、调色合法、缺少侧面、元数据和许可证齐全。同配置同版本产物可复现。改变头发和服装时要求头像与地图小人在发色、轮廓、主色和配饰上对应；不只是任意两张图共享一个名字。

工具说明需提供一个“修改发色并导出”的完整示例和一张前后对照图。其他模型先复制样例、列出可用部件，再修改配置；不能只能通过猜源码中的隐藏 ID 操作。

### 9.5 可选 MCP 外壳

如果之后需要自然语言模型直接调用，可在同一核心上增加 `character.listParts`、`character.validate`、`character.render`、`character.preview`。该外壳只包装本地工具，不控制正式游戏钱包和存档，也不把 MCP 作为唯一入口。本轮不安装或配置该服务。

## 11. 分阶段交付与接口落地顺序

| 阶段 | 交付 | 通过标准 |
| --- | --- | --- |
| 0：冻结基线 | 记录认可的行走样例、旧版卡面和常用流程清单，确定 v2 DTO | 不把未批准的画像或演示资金当正式需求 |
| 1：视觉竖切片 | 新壳＋地图行走＋采购目录＋卡面市场＋一张详情；先 Mock | 1366×768 可直接看图、选货和核对交易，字号与像素达标 |
| 2：人物工具标准化 | JSON Schema、CLI、预览器、三套一致外观、许可输出 | 另一模型仅凭 README 可改色、选部件、导出和导入预览 |
| 3：后端展示视图 | ArtRef、商品／卡片聚合、统计摘要和分页，兼容 1.0 | 每个需要卡面的页面拿得到真实图像字段 |
| 4：交易竖切片 | 采购→到货→签收→开包→保留→挂牌→真实成交 | 钱、实物、订单、卡面和动画结果一致；失败不产生部分假成交 |
| 5：经营整合 | 零售、NPC、垃圾桶、对战房、任务、经营、存档 | 新 UI 不损失现有业务能力，暂停与换房正确 |
| 6：入口切换 | 主模型合并和切换根入口，保留回退入口 | 不清档，不新建旁路收藏，开发启动稳定；exe 另行决定 |

实现时先完成最常用的一条闭环，再补齐其他页。不要先画二十个静态窗口，最后才发现卡面字段、交易原子性或站位契约不适用。

## 12. 验收清单

### 12.1 画面与卡面

- [ ] 人物与本次认可样例保持相同占地和步态；上、左、下、右索引正确，无“没脸的正面”。
- [ ] 斜向速度一致，侧面清楚，停止不踏步，切房不重建角色。
- [ ] NPC 姓名＋类别可读；密集站位时标签不遮成一团。
- [ ] 1366×768 下买卡、卖卡、收藏、开包结果、垃圾桶和阵容默认都能直接看到卡面。
- [ ] 商品包／盒有各自包装；不同主题可辨认；首屏不堆长版本号。
- [ ] 详情大图与技能清楚；缺图不会导致物品卡塌陷或拿错卡代替。
- [ ] 真正像素素材近邻显示，武将原画和中文正常显示，缩放没有整体糊掉。

### 12.2 操作效率

- [ ] 添加第二件采购商品不丢第一件；结算始终可见，不逐项展开询价表。
- [ ] 多笔到货可统一签收；在途和已收不混进待收集合。
- [ ] 在详情与列表间返回不丢筛选、滚动、选择和草稿。
- [ ] 批量留一、上架、拾取和拆包存在且有可理解的真实预览。
- [ ] 需要走到柜台时能自动关闭交互暂停、走过去并恢复原页。
- [ ] 主要操作有键盘与点选入口，输入框不会带动人物移动。

### 12.3 业务与兼容

- [ ] 多行报价的资金不足、挂单售出、库存被锁和价格变化均可定位到行；整笔不部分执行。
- [ ] 重试请求只成交一次；超时可补查；读档不复用旧分支操作。
- [ ] 收藏总数与实物副本一致；状态重叠不被重复计数。
- [ ] 旧盒内容、印刷档位、已付款订单和已存日档保持；停产主题不重新发行。
- [ ] 挂牌无即时收入；成交、营业额、成本、现金和服务费命名准确。
- [ ] 未知胜率和趋势不编造；赌注受正式能力限制。
- [ ] 页面暂停不使真实牌局无法出牌，关闭一层不误解除其他暂停。

### 12.4 工具可交接

- [ ] 人物配置有版本，工具有 CLI、说明和可复现示例。
- [ ] 其他模型不需要当前对话即可找到所有部件 ID、方向行序、落脚点和许可。
- [ ] 依赖独立锁定、路径可配置，不要求本机隐藏缓存已安装好。
- [ ] 产物含 PNG、atlas、配置和署名，图像与清单尺寸相符。

验收重点是上述用户流程、图片可见性和业务边界。使用已有业务测试保证守恒，新增一条正式前端交易竖切片和必要异常场景即可；不为每个颜色、圆角或纯展示标签堆重复测试。
