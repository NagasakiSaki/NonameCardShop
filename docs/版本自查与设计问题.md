# 版本自查与设计问题

日期：2026-10-23。基线：集成版 `80318df9`。范围是新版正式 Host、经营/牌局异常流程、存档与性能，以及经济和长线设计；没有重建 exe，没有操作玩家现有进度。测试全部使用临时世界与独立浏览器上下文。

## 判断

当前适合进入内测，主要玩法已经接通，但仍是经营原型。之前的正常流程通过，不代表异常路径都正确；本轮确实复现并修复了一批问题。以下把已修复代码缺陷和仍待设计的内容分开。

## 本轮已修复

| 问题 | 原后果 | 处理 |
| --- | --- | --- |
| 垃圾桶卡仍符合参赛筛选 | 不捡回就能参赛、占用垃圾桶实物 | 参赛副本必须位于 collection，仍需流通和解锁条件 |
| 没真正开局就认输 | 推进“亲自完成比赛”任务；与取消语义冲突 | 未开始比赛按取消退款处理，不记比赛与战绩 |
| 同一玩家可同时登记两桌 | 实物、桌位和 NPC 被多场占用，界面只能管理其中一场 | 后端限制一场未完成的玩家比赛 |
| 等待下一局时点“本局认输” | 意外判整场输 | 拒绝没有真正开始的小局认输；按钮按引擎 ready 状态更新 |
| 打烊后还可开赛或买卡/交付 | 已结日账又发生收支 | 新开赛仅营业中；结算后暂停相关资金交易 |
| 缺字段或错误金额的存档可被导入 | 正常世界可能被替换为下一 tick 就报错的世界 | 增补核心结构、价格、累计进度、战绩数据校验；失败不提交 |
| 读档后重试旧操作返回旧成功 | 返回旧分支的成交/开包成功，但新分支没有该结果 | 成功记录标记 worldId/branchId；跨分支重试报 STALE_OPERATION，补查返回 stale |
| 并发挂载、载入期间关窗 | 可能挂两份 iframe，或在已关闭窗口持有暂停令牌 | 挂载互斥、AbortSignal、关闭取消、幂等清理；增加引擎错误/载入超时恢复 |
| 窗口并发刷新 | 异步查询结果可能叠到已刷新界面 | 每个窗口串行刷新，关闭后不再渲染 |
| NPC 后台比赛挡住保存 | 开存档面板会暂停 AI，同时又要求 AI 先结束，体验容易卡住 | 允许保存/读取后台比赛；仅保存经营与比分，NPC 当前小局在读档后重开，提示清楚；玩家正在运行的小局仍先关视图或打完 |
| NPC 仅按钱包购买 | 普通卡/包可被标成接近顾客全部预算仍卖出 | 单卡按参考行情、密封商品按冻结建议零售价限制接受上限；默认各 1.4 倍，可调；跳过过贵商品继续找合理商品 |
| 供应商信用在 UI 无法启用 | 后端有额度，缺钱时前端仍固定禁止使用 | 报价返回剩余额度，玩家主动勾选；只给不足货款记欠款，不生成可花现金，收入优先还款 |
| 订货数量前后端上限不同 | UI 允许 40，实际最多 20，询价失败 | UI 统一为每单最多 20 包/盒 |

旧版五档/旧卡池没有在本轮重新启用。NPC 价格上限不修改既定卡盒内容、印刷稀有度或已下单成本。

## 存档和性能修正

原经营 tick 每 250 ms 深拷贝整份 record，历史日档也包含在里面；IndexedDB 还重复写入所有历史日档。它在空店时不明显，库存与日档增加后会放大。

现在只复制可变世界与容器；不可变历史日档按 ID 独立存于同一 IndexedDB 的同一对象仓库，活跃记录仅保存日档元数据。新增/修剪日档与活跃世界在同一事务中提交。旧的内嵌日档自动转存；失败不产生孤立半档。没有更换或清空数据库。

本机一次结构复制基准（30 份日档、每份 3000 条模拟实物，5 次均值）约为 **118.4 ms → 3.44 ms**。这是结构复制耗时，不是整场游戏帧率。行情更新也从“每个卡种遍历所有库存和日志”改成一次聚合再查询，公式保持一致。

仍需后续长档压力测试：启动时会读取历史日档，当前世界本身仍定期持久化，实物、历史比赛及操作记录也会逐渐增加。不能凭短流程测试宣称几万张卡、上百个分支都稳定。

## 尚未修改的设计问题

### 1. 开包收藏路线会占住流动资金

用现有真实配方做 100 组固定种子估值：买十包标准散包成本 1200，全部打开后“每种印刷版留一”，剩余卡按参考价计算的可挂牌估值为 **329～869，平均 533.42**。这是估值，假设剩余卡都能按参考价成交；实际现金还受买家、时间与预算限制，不保证回款。

因此新手若把 1200 全开掉再留一，很容易陷入“收藏有价值，现金不够进货”。下一轮应优先做现金目标与库存引导，明确密封零售养店、开包收藏占用资金；现有信用额度只是缓冲，尚无完整破产/复苏流程。

### 2. 长期任务与编辑接口还不够

新版目前主要是 7 个累计型入门任务，不是成熟的按天经营任务流。连续营业额、净利润/现金、库存周转、顾客满意度、长期店铺升级和失败后的替代目标都没有形成循环。

任务仍在 `runtime.mjs` 的 tasks 数组中，新配置编辑器只接规则与管理配置。下一轮应拆出 backend-tasks 配置、条件/奖励类型与任务版本，并接入 config.list/validate/apply；不能把旧 legacy 任务编辑器当作已经接通新版。

### 3. 顾客决策仍偏简单

本轮堵住了任意高价卖给 NPC 的漏洞，但现在仍是预算和接受上限驱动，可能诱导玩家长期把价格推到上限。不同客群的价格敏感度、稀有度/阵营偏好、耐心、到店目的、回购频率和满意度，需要再做可调的需求模型。

暂不声称当前模型模拟了成熟的二级市场。

### 4. 胜率会受选对手与重开行为影响

目前玩家可以选择弱阵容、在无赌注中断后重开当前小局；BO3/KOF 已分开，但玩家局和 NPC 局尚未作为不同质量的样本建模。战绩会影响行情，因而现阶段只能把它视为本存档环境下的经营信号，不是客观竞技排名。

完整事件栈/随机状态恢复和公平退赛处理完成前，下注继续关闭。特殊技能也没有全目录实测；加载超时能恢复，不代表所有技能局内逻辑均已兼容。

### 5. 评分和收藏价值需要进一步分层

统一评分解决了“同一强度在不同主题里被分成不同档”，但多数武将仍是规则初估。把高评分直接等同高稀有度，可能令低档阵容和后期收藏目标趋同。

之后应区分模式强度、数据可信度、印刷/收藏价值和市场热度，做版本化校准；本轮没有擅自重划稀有度或重调核心出货率。

### 6. 大库存体验仍有边界

单张出售、丢弃选择器只展示前 200 个实物；背包有聚合/分页，留一批量操作覆盖完整集合。将来需要可搜索的副本选择器、仓库分组、批量标签和更清晰的价格/利润提示。当前是可用上限，不是最终库存交互。

## 验证与复现

- `npm run test:audit`：11 个业务异常场景、引擎挂载取消/互斥/超时/来源校验，以及真实 IndexedDB 的旧日档转存、重连、事务失败与修剪。
- `node tests/frontend-integration.mjs`：本轮重新验证正常经营链、真实原引擎 BO3、日结与档案文件读写；新增确认引擎 ready 后“本局认输”可用。
- 基础后端、设施/NPC、视图守恒检查通过；没有跑旧版全套或重建 exe。
- `node tools/audit-prototype.mjs`：复现固定种子估值与结构复制基准，输出到 `.local/game-audit/measurements.json`；不连接真实世界、不写玩家档。

本轮排查覆盖确定性异常流程和一个真实营业/对局流程，不等同于长时间真人试玩或全武将技能回归。
