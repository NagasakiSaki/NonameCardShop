# Phaser 长期维护与优化约定

日期：2026-10-24。状态：用户已确认采用当前 Phaser 路线。本文件规定后续开发方向，不表示下面的工具、拆分和优化已经全部完成。

## 1. 技术决定

继续使用 Phaser 展示像素世界，HTML/CSS 展示交易与信息界面，JavaScript 经营模块提供权威规则，保留现有无名杀对战接入与 Electron 桌面路径。

不安排 Godot 迁移或双引擎并行维护。以后只有在可复现需求、实际测量和接入成本表明现有路线无法合理满足目标时，才重新评估技术路线；画面风格调整或个别 bug 不直接触发重写。

Phaser 版本与 vendor 文件保持当前基线。修补与升级由主模型集中进行，记录来源、版本和兼容影响；外部模型不自行替换。生产运行继续使用本地依赖，不引入运行时 CDN。

## 2. 模块责任

| 层 | 当前入口 | 长期边界 |
| --- | --- | --- |
| 规则与状态 | `modules/backend/`、`data/backend-*.json` 等正式配置 | 持有资金、卡牌、访问、比赛、任务与档案；不依赖 Phaser/DOM，不从动画推导成交 |
| 契约 | `contracts/card-shop-host.d.ts`、`contracts/README.md` | 查询、命令、错误、事件和单位的共同依据；新增字段先定语义 |
| 正式适配 | `frontend/host/`、`frontend-next/services/` | 将真实状态转为展示数据，处理报价、重试与分支；不再造一套经济 |
| 世界展示 | `frontend/scenes/`、`frontend/world/` | 镜头、动画、深度、标签、灯光和输入意图；显示状态不是业务事实 |
| 交易与信息 | `frontend-next/screens/`、`components/`、`frontend/ui/` | 纯展示与用户操作；库存与金额以 Host 为准，交互暂停统一管理 |
| 装配 | `frontend/app-shell.mjs`、`frontend/main.mjs` | 建立连接、组装模块和路由；后续新增业务不继续堆进外壳 |
| 素材生产 | `tools/frontend-art/`、`tools/character-kit/`、`tools/portrait-kit/` | 源图、配置、生成物和导入分开；可重建、可追溯 |
| 对战适配 | `integration/` | 隔离原无名杀与店铺生命周期；不直接散改 vendor 技能或引擎 |

新增组件优先接收只读 view 与注入 actions，并提供 update/dispose；这不是新增 Host 协议。小型组件不要求全部框架化，不为了整齐一次重写所有老页面。

旧 `modules/*.js` 和 legacy 页面有自己的历史架构；不能直接把旧模块说明当作新版 Host 的调用规范。新增功能以当前正式入口和 contracts 为准。

## 3. 接口与存档兼容

- 默认采用兼容扩展：旧字段不随意改名或改变含义；确需破坏兼容时提供版本、迁移与旧入口处理。
- 游戏币为整数；未知、0、尚未到账、预留与欠款分别表达；模拟战绩与真实对战记录保留来源区别。
- command 继续使用稳定 requestId、权威报价/预览及世界分支校验；结果未知先补查，不能重新扣款或重新抽卡。
- 存档保存业务状态，不保存 DOM、Phaser 对象和动画句柄。需要新持久字段时，同时定义默认值、旧档迁移与日初恢复语义。
- 商品发行、印刷、价格和任务规则的版本分别记录。默认配置调整不能改写已经买到的盒内内容、旧订单和历史成本。
- 新事件/任务的随机结果与完成标记需要可恢复；渲染、开关窗口和现实计时器不能发奖或推进经营。
- 交互暂停、手动暂停与其他暂停原因统一计数。世界时间、顾客、模拟比赛和耐心一致冻结；UI 动画不承担营业时钟。
- 读档、切换档案、重连与销毁时，清理订阅、输入、窗口和旧操作上下文；不让旧异步返回覆盖新世界。

## 4. 素材和地图的维护

- 保留 64×64 四向八帧行走、128×224 立绘、96×96 头像的当前正式基线；改规格需同步 manifest、工具、预览和导入校验，不能仅改图片。
- 用户原图只读。正式素材有稳定角色 ID、来源、参数和哈希，不能把源码生成物和原图授权混写。
- 源文件与配置是维护入口。不要只手工修生成 PNG 却不记录覆盖方法，导致下次重建还原。
- 地图区分图形层、前后遮挡、碰撞、交互站位、排队点、入口与出口；所有通行改变需同步主模型导航。
- 设施逐渐采用可复用定义：素材、状态图、锚点、建议占地与交互类型；库存和服务能力仍来自业务模块。
- Tiled 或其他可视化编辑器可在实际需要时接入，通过导出适配到现有地图格式；不能让编辑器专用字段无校验地替代运行契约。
- 保留正式资源与试验预览的隔离，候选通过审查后统一导入。缺失素材提供占位与日志，不让整个游戏停在黑屏。

## 5. 性能优化的观察方法

当前代码使用 `Phaser.CANVAS`，地图背景预绘制、家具与人物分层；这是实现基线，不代表存在已测出的性能瓶颈。切换 WebGL、加入对象池或更换渲染路径前先比较实际表现和兼容性。

未来建立少量可重复场景：普通营业、当前合法容量下的繁忙店面、反复打开关闭交易窗口、较大库存查询、长时间营业/跨日。测试使用隔离档案，人数与库存规模写明，不把突破设计容量的压力场景当普通体验。

每份性能记录至少写：提交、浏览器/桌面运行时、硬件、视口、渲染器、资源版本、在场人数、世界倍率和暂停状态，以及冷/热启动区别。

观察帧间隔与长帧、输入反馈、交易面板首屏时间、查询耗时、内存变化和存档耗时。60 fps 可作为普通营业的体验目标，不能在没有指定硬件和测量时声称已经达标。

现有 `tools/frontend-art/probe-perf.mjs` 只有短时 Mock 帧数观察，可作起点，不能证明真实交易、长时间营业或内存稳定；后续按实际卡顿补充，不在每次改文案时运行性能全测。

优先排查以下候选热点，必须通过测量确认后再改：

1. 每帧全量同步人物、创建临时数据、更新不变文本或灯光；可评估按 revision/脏标记更新。
2. 长卡表/成交记录一次生成全部 DOM；沿用分页，确有需要再引入虚拟列表。
3. 图集与大图重复解码、预载所有非当前资源；合理分批加载，同时保证换肤/开窗无明显闪烁。
4. 关闭窗口和换档后的监听、计时器、订阅或贴图未释放；先定位持有者，再决定缓存生命周期。
5. 高频世界推送和低频经营查询互相拖慢；展示刷新频率可分层，业务时钟与结算保持原义。

优化不能通过丢失顾客、跳过费用、缩短暂停或降低卡面质量掩盖问题；也不为当前小规模店面提前搭复杂并行系统。

## 6. 长期可调内容

前三日进程、熟客需求、市场事件、任务奖励和升级逐步数据化。每类配置说明字段、范围、前提、可重复性、历史版本及缺字段默认值，增加有意义的示例和必要 schema。

同一内容 ID 发布后保持稳定；文案、图形、触发条件与奖励引用分开，方便以后改任务和换皮。还未实现的配置项必须标注，不能在编辑器放一个没有效果的按钮。

避免一次创建庞大的通用任务引擎。先支持前三日与一类熟客事件，第二个真实用例出现后再抽取公共结构。

## 7. 验证与发布

- 按改动选择检查：素材看图与资源检查；界面看关键操作/窗口清理；业务看金额、实物和幂等；存档看迁移与日初恢复；对战桥接看对应模式。
- 文档、文案和低影响样式不跑完整经济/真实对战。已通过的检查只在代码继续变化、失败或存在未解决风险时重跑。
- 开发端、桌面开发端和玩家正式进度继续隔离。`?tradeUI=classic` 只是旧界面参考，仍用同一世界，不能当安全测试档。
- 每个版本写明改了什么、怎么验证、旧档影响、资源/规则版本和已知限制。实验可用独立入口，正式默认入口只有主模型切换。
- 故障回退要同时考虑代码与数据：新版本写过存档后，直接回滚代码不保证可读；先保留升级前导出/自动备份，已成功迁移的数据不要静默降级。
- 私有发布沿用 `npm run publish:private`，保留当前安全导出流程；测试与候选素材目录不整包上传。EXE 等开发版稳定后单独发布。
