# 02：接口兼容、赛制扩展与内核升级合同草案

**状态：设计提案。本文新增类型、目录、查询和命令尚未实现。** 现行正式合同仍是 `contracts/card-shop-host.d.ts` 与实际实现。MV5-07/11/12/14 先交合同差异和最小样例，主模型冻结首版后，下游按冻结文档实现。不得把本文 API 名当成已存在后端来写“接入成功”。

## 2. 分层目标

```text
Phaser 场景 / DOM 窗口 / 内容配置
                  ↓ 只读视图 + 业务意图
现有 Host：库存、钱、流通、队列、比赛、任务、存档
                  ↓ 规范化的比赛计划与结果
赛制注册表 / 赛事编排 / 考核规则（互相独立）
                  ↓ 能力要求与 launch plan
EngineFacade → 对应 EngineAdapter → 被锁定的无名杀运行包
                  ↑ 带会话标识的标准事件
             唯一持久结算点（Host）
```

不要求按图一次搬空现有文件。先给当前桥接加外观层并保持行为，再逐个搬模式分支；经营代码不能 import 新版 `lib/game/ui`。不支持的模式/考核必须在报名扣款前拒绝并说明原因。

## 3. 六种版本分开保存

| 版本 | 表示什么 | 生效边界 |
| --- | --- | --- |
| `hostContractVersion` | 前端与 Host 消息结构 | 现有 `card-shop-ui/1.0` 兼容增字段；破坏性变化单开主版本与适配 |
| `saveSchemaVersion` | 持久数据结构 | 纯迁移函数，旧输入保留，成功后再写新副本 |
| `engineProfileId` | 上游运行包 + adapter + 内容清单 + 构建哈希 | 一场比赛开局后固定，不能中途换引擎 |
| `formatId/formatVersion` | 对局规则 | 报名/比赛冻结；不靠全局当前值回写旧对局 |
| `contentRevision` | 武将/技能/素材定义与映射 | 显示和实际载入可核对；改版差异显式记录 |
| `economyRevision/printVersion` | 数值配置与已发行实物 | 新发行/次日按政策生效；旧卡/盒/成本不追溯改写 |

版本是结构化字段，不把任意目录名或一个 semver 字符串当成全部兼容信息。原 cardKey 不因安装新内核直接批量改前缀。

## 4. 赛制与赛事：拟定最小结构

```ts
type FormatDefinition = {
  schemaVersion: 1;
  formatId: string; formatVersion: number; title: string;
  participants: { min: number; max: number; teamSize: number };
  roster: { slots: number; uniqueGeneral: boolean; policyId: string };
  matchStructure: { kind: 'single' | 'bestOf' | 'relay'; targetWins?: number };
  rulesHandlerId: string;
  requiredCapabilities: string[];
  timePolicyId: string;
  statisticsPolicyId: string;
};
type EventDefinition = {
  eventId: string; revision: number; formatRef: {id: string; version: number};
  schedulePolicyId: string; eligibilityPolicyId: string;
  feePolicyId: string; rewardPolicyId: string; cancellationPolicyId: string;
};
```

上述为 DTO 草案，不是放任任意脚本进配置。handler/policy 是受支持注册表的稳定 ID，配置不 eval 函数。第一版只需复刻 KOF/BO3，并增加一个快速单局或主题规则；多人能力未实现就不注册为可用。

保留旧 `combat.eligible/preview/register/joinQueue` 的 `mode:'bo3'|'kof'` 兼容输入，内部映射到对应 formatRef。拟增 `formats.list/detail`、`events.list/detail`、`assessments.list/detail` 只在正式绑定后开放；旧窗口不用同步重写才能营业。所有列表仍分页、可搜索，不把无限候选塞快照。

事件状态建议：`draft → announced → registration → locked → running → settling → completed`；另有 `cancelled/expired/attention`。报名锁阵容与预留资金、活动开始收入、奖池托管、退费、正式比赛、赛事总奖励是不同记录。赛事调度复用 matchId，不复制一套战斗结算。每一轮可含多个 match，每个 BO3 match 可含多个 bout；时间与奖金分别按批准的层级恰好结算一次。

## 5. 引擎适配器：拟定职责

```ts
interface EngineAdapter {
  adapterId: string; adapterApiVersion: 1;
  describe(profile: EngineProfile): CompatibilityReport;
  probe(environment: ProbeContext): Promise<CapabilityReport>;
  resolveRoster(input: StableRoster, content: ContentMap): ResolveReport;
  buildLaunchPlan(input: FrozenMatchPlan): LaunchPlan;
  normalizeEvent(raw: unknown, session: SessionBinding): NormalizedEvent | RejectedEvent;
  disposeSession(session: SessionBinding): Promise<void>;
}
```

生命周期挂载继续由 Facade/现有 battle mount 统一管理，不让 UI 自己选端口、读 vendor 或改 lib。adapter 仅认识自己支持的上游；多个 profile 可共存，不在业务层加一串版本 if。

`EngineProfile` 至少记录：上游 repository/ref/commit、发布件与内容 sha256、游戏版本来源、adapterId/version、构建工具/锁文件/入口/资源映射、清单摘要、支持的 capabilities、状态（staged/verified/active/retired）、本地槽位。大型文件清单外置，不塞存档与快照。

能力分层：静态文件存在、模块加载、真实 ready、正常出牌/响应、结果、BO3 连局、KOF 换将/手牌继承、托管、后台执行、观战、回放、完整恢复等。**未测试不填 true。** `replay` 与 `resumeExactState` 分开；当前中断后重新发牌不能叫精确恢复。

## 6. 标准事件与结果来源

事件信封草案至少有 `schemaVersion/worldId/branchId/matchId/boutId/sessionId/engineProfileId/seq/type/payload`。window.postMessage 的 origin、source frame、会话绑定和递增 seq 都要验证；信封中自称可信不等于来源可信。保留旧消息版本的 adapter，不放宽现有校验来“兼容”。

结果 provenance 需区分：

- `engine-played`：实际引擎完成，另记玩家/AI/辅助、规则/内核/阵容和事件证据。
- `simulated`：经营用模型结果，另记模型版本、seed 和适用范围。
- `test-fixture`：受控死亡、注入胜负、合成数据，永不进入真实玩家经济、资格或市场统计。
- `imported/legacy-unknown`：旧档无法证明来源，不冒充新增真实战绩。

同一个结果 ID 重放、断连重试、迟到帧、读档分支、第三小局旧事件都不能再次入账/晋级/推时间。已截断详细日志不影响去重和累计统计；业务投影不依赖 UI 打印日志是否存在。

## 7. 稳定卡身份与旧发行

拟定层次：稳定 `cardDefinitionId`（含版本变体身份）→ 各 contentRevision 下的定义 → engineProfile 中的 generalId 映射；真实卡还保留 inventoryRef、旧 cardKey、printVersion、printedRarity、原成本与来源。

不能只把所有 `noname-1.11.6:名字` 去前缀：同名、不同版本武将、重命名、拆分/合并、移除和技能替换都需显式映射。默认可一对一的映射也须有证据；冲突项进入人工待决表，不从稀有度或显示名猜对应。

旧卡的印刷稀有度/盒内容保持原样；对战采用哪一版技能由赛事冻结的 rules/content/profile 决定。默认候选政策：新的受支持赛事用当前验证规则，说明旧卡在当前规则下的变化；历史比赛保留原 profile 引用。不为保留旧卡强行永久冻结所有可执行技能，也不无提示替换已报名赛事的技能。用户若要旧版怀旧赛，作为显式规则 profile 单独支持。

新内核缺少某牌：卡仍在收藏/旧市场记录中，显示缺少当前赛制支持，可选旧 profile 或从报名阵容移除；不删除实物、不自动换成别的武将、不收了报名费才报错。新上游内容先经过用户的主题排除表、兼容与强度评审，不自动把排除主题重新加入进货目录。

## 8. 升级流水线与回退

1. **识别**：记录当前 profile、上游固定 ref、SHA/清单与发行说明。默认针对稳定发行评估；开发分支只作隔离试验。
2. **暂存**：下载/提取到本包 sandbox 或未来专用 staging，不在活动 `vendor/noname` 原地解压。不纳入 Home/浏览器缓存/用户配置。
3. **构建**：按被固定版本的官方步骤，锁依赖、工具版本和输出；上游需要构建时用产物，不把源码树当运行包。记录来源说明和分发所需许可证/NOTICE，不在本轮替用户做法律结论。
4. **探测**：静态路径 → 真实加载/ready → 代表技能/结果 → 已支持模式 → NPC/玩家隔离 → 资源/桌面路径。当前与候选 profile 同场景对照。
5. **差异报告**：新增/删除/改名武将、技能与图源变化、API 缺口、旧档/价格/发行影响、失败能力和可回退版本。不要把未测卡标全兼容。
6. **迁移预演**：仅复制存档，在副本上做身份/协议升级，生成报告和备份哈希；不修改唯一旧档。
7. **激活**：在无活动比赛、无未定交易、允许切换的存档边界执行原子配置切换；推荐下个营业日启用新内容/经济。更改端口和 slot 不使旧事件变成新场赛果。
8. **回退**：恢复旧 profile 与对应存档副本；若新档已发生旧格式不支持的数据，不伪造无损降级。升级工具需明确“只回退运行包”与“恢复升级前进度”两个不同选择及损失。

工具目标是一次选版本后自动完成检测与报告，合格时切换；不自动接入上游每个更新，不碰运行中比赛。网络失败、哈希不符、构建失败、缺少适配器、迁移冲突都留在 staged 状态，现有游戏继续用旧 profile。

## 9. 存档、市场和完整恢复

当前日初存档语义继续保持：读取某日回当天开始；即时备份另列，不冒充日初。新增赛事、预留、晋级、随机/模拟种子、统计版本必须随快照恢复。实际引擎状态是否可恢复由能力探针证明，无法证明就标为 interrupted 并提示重开本局，不能默认清锁后当作未发生。

升级不能自动删除收藏、清市场、重领赠盒/任务奖，不能将曾流通事实丢失。市场统计若跨规则/内核版本比较，默认分桶展示，按明确政策衰减/重置行情影响；旧历史仍保留。新评分只能影响批准的新版发行/参考，不回写旧印刷与已接受合同。
