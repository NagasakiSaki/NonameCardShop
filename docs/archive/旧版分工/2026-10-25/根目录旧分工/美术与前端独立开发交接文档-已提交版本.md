日期：2026-10-23

基线：源码 v0.8.1，本地提交 `6d8c627a7eb9904b505633467922d20332e7a634`。

协作契约：`card-shop-ui/1.0`，本文件为拟定规范，相关新目录和接口尚未实施。

**交接对象：负责美术与前端的另一模型。后端、业务规则、数据和最终工程合并由当前主模型负责。请先完整阅读分工与接口章节，再开始写代码。**

## 0. 可以直接发给前端模型的任务说明

请基于本项目完成新版像素 RPG 卡店的美术、地图、四方向行走动画、页面和交互。风格参考早期宝可梦的彩色俯视 RPG 观感，先采用 GBA 方向做原创样板。店长和不同类型顾客必须有不同的地图角色与对话立绘。

你负责 `frontend/`、`assets/frontend/`、`tools/frontend-art/`、`tests/frontend/` 和 `docs/frontend-handoff/` 内的新增文件。不要修改原根目录入口、原业务代码、原引擎、正式卡表、评分、概率、价格、存档或根依赖。用本文的 Host 接口与 Mock 独立完成界面。真实规则与正式 Host 由主模型实现，最后也由主模型接入、联调和合并。

交付的应是能运行、能操作的前端工程、可复现的美术源文件与生成工具、Mock 场景和交接清单，不是只有设计图或一张背景图。没有真实接口时，明确显示 Mock 模式；禁止通过直接修改正式状态假装完成交易。

本轮用户只要求编写本交接文档，尚未要求主模型立即实施上述工程。

## 1. 最新需求与优先级

用户最新确认覆盖之前草案的两点：

1. **可以清空旧存档，下一开发阶段可以从新世界开始。** 不再要求迁移旧版五档稀有度、旧订单和旧市场数据。清空功能由主模型实施，前端模型不得自行删除任何真实进度或整个浏览器存储。
2. **稀有度必须先基于全局卡牌评分统一划分。** 不能在每个主题包内部各选一批“最强的当 SSR”；卡包价格和包内配比要随其实际卡池强度分布动态生成。它不是仅改四个稀有度名称或统一给所有主题套同一套配比。

现阶段需要实现的最终体验：

- 主角是店长，可用 WASD/方向键、触屏方向键和点击寻路操作。
- 正店售卖密封卡包与卡盒；单卡在另一处二级市场柜台交易。
- 柜台进货、签收、拆盒与开包，支持一键开包和“留一，其余上架”。
- 独立对战房，NPC 入座打牌，店主收开桌费与抽水，也能参赛。
- 参战武将受本世界流通与持有规则约束，不再展示“单挑专用卡池”。
- 四档稀有度：N、R、SR、SSR；展示统一全局评分、样本量和真实后端报价。
- 所有交互面板期间自动暂停经营世界；真实战斗仍可正常出牌。
- 昼夜画面随游戏时间变化；垃圾桶物品到次日清空，清空前可捡回。
- 按天存档仍保留，新系统从新档开始；本阶段不打包 exe、不制作更新器。

## 2. 当前工程事实：为什么必须隔离开发

项目根目录为 `D:\GameDev\NonameCardShop`，可整体移动。现有入口是根目录 `index.html`；Phaser 已在 `vendor/phaser/phaser.min.js` 本地提供。现有 UI 主要使用原生 JavaScript、HTML 和 CSS，没有 React/Vue 构建链。

目前不是一个前后端边界已经完全干净的项目：

- `app.js` 同时负责启动、收藏 UI、开包展示和存储入口。
- `shop.js` 同时负责 Phaser 场景、移动、NPC 购物流程和商品成交。
- `business-ui.js`、`management-ui.js`、`battle.js` 也直接访问业务状态。
- `modules/`、`shop-state.js`、`shop-business.js`、`shop-tasks.js` 管理经营规则。
- `server.mjs` 提供本地静态服务与引擎运行地址，原战斗由独立无名杀页面执行。
- 当前没有本文所说的新 Host、独立前端或新版评分/动态产品接口。

**因此，不要在原 `shop.js` 或 `app.js` 上边改画面边保留业务写入。** 前端新建独立入口，主模型在原代码侧提取业务和接入适配器。双方不共同编辑上述混合文件。

本文件中“后端”指权威的业务层、状态、规则与引擎适配，既可能运行于浏览器，也可能运行于本地 Node 服务。不要为了符合名称而强制重写成网络服务器，也不要因为规则在浏览器里就认为可以由前端自行修改。

## 4. 总体结构与真实接入方式

```text
前端模型负责                        主模型负责
┌─────────────────────┐           ┌─────────────────────────┐
│ Phaser 场景 / 像素资源 │           │ 正式 Host 适配器          │
│ HTML 面板 / 输入管理  │──查询/命令→│ 规则 / 钱包 / 库存 / 时钟  │
│ 加载 / 错误 / 动画    │←快照/事件──│ 市场 / 评分 / 产品 / 存档  │
└─────────────────────┘           │ NPC / 对局 / 无名杀接入   │
           ↕ 开发替身              └─────────────────────────┘
     frontend/mock/mock-host.mjs
```

业务视图只依赖一个 Host 实例。Mock 与正式 Host 对上层提供相同方法，不能到处写 `if(mock)` 分支。

- 预览模式明确使用 `?mode=mock&fixture=...`，在画面上显示“前端演示数据”。
- 正式模式由主模型提供 `integration/frontend-host.mjs`，通过动态导入加载；该文件本轮并不存在。
- 正式接口缺失或连接失败时展示连接错误与重试，**不静默切换 Mock**。
- 前端内部选中项、搜索词、分页、窗口位置属于 UI 状态；钱包、库存、稀有度、统计和交易属于 Host。
- 前端可以为行走做视觉插值/预测，但不能因为“动画到柜台了”就自行成交或发奖。

工厂导出名固定为：正式模块导出 `createHost()`，Mock 模块导出 `createMockHost({fixture})`，均异步返回 Host 实例，不在工厂内部自动 connect。前端入口负责统一连接：

```js
const params = new URLSearchParams(location.search);
const host = params.get("mode") === "mock"
  ? await (await import("./mock/mock-host.mjs")).createMockHost({
      fixture: params.get("fixture") || "store-day"
    })
  : await (await import("/integration/frontend-host.mjs")).createHost();

// 外层启动器负责捕获导入/连接错误并显示重试页。
const connection = await host.connect({
  contractVersion: "card-shop-ui/1.0",
  clientId: crypto.randomUUID()
});
```

`clientId` 在该次页面会话内保持稳定，重试连接复用；不要每个按钮点击都重新创建 Host。正式 Host 的 `capabilities` 未开放的业务，在页面中显示明确的未接入状态，不绕过 Host 调用旧逻辑。

### 4.1 接口兼容与变更

本文约定契约 `card-shop-ui/1.0`。主模型会按本契约落地正式接口；若发现接口不足，前端先在 `docs/frontend-handoff/接口缺口.md` 写出页面、问题、所需字段、示例，不直接修改后端。

新增可选字段可兼容；删除字段、改变金额单位、改变字段语义或命令结算方式属于破坏性变更，必须更新契约版本并由主模型协调。Mock 不得擅自成为另一套规则来源。

## 5. 美术规格与素材交付

### 5.1 样板先行

先交付并预览：店长四向行走、一名新手顾客、一名收藏家、一段柜台、一组地板墙面、主店小区域、背包/卡牌详情样式。样板通过后再扩展全店与对战房。

目标：清晰的原生像素、统一色板、轮廓、俯视角和人物比例。不是把大幅插画缩小后称作像素画，也不是给旧单张人物上下晃动。

默认设计参数用于独立开发；最终风格可在样板阶段统一调整：

| 项目 | 默认规格 |
| --- | --- |
| 基础瓦片 | 16×16 原生像素 |
| 地图角色 | 每帧 24×32；底部落脚点一致 |
| 行走图集 | 3 列 × 4 行，共 12 帧，72×128 PNG，透明背景 |
| 方向行序 | 第 0 行下、第 1 行左、第 2 行右、第 3 行上 |
| 帧序 | 每行中间列（索引 1）为待机；行走按 0→1→2→1 循环 |
| 锚点 | 帧内 `(12,30)` 为地面落脚点，角色物理坐标指向该点 |
| 对话头像 | 96×96；与地图角色同一发型、衣服和标志物 |
| 房间 | 初版各 30×20 格，480×320 原生像素；需要时扩大地图配相机 |
| 默认显示 | 1×/2×/3×整数倍，最近邻采样，关闭抗锯齿与纹理平滑 |
| UI 字体 | 正文使用清晰中文字体；标题可带像素风，但技能正文不牺牲阅读 |

12 帧是最低完整交付，不包含额外表情、动作的要求。可以增加帧，但需在资源清单中声明；不能依靠水平翻转冒充上下方向。

### 5.2 第一批角色

| 角色 | 视觉特征方向 | 必交素材 |
| --- | --- | --- |
| 店长 | 围裙、钥匙或店徽，主色明确 | 四向行走 + 待机 + 独立头像 |
| 新手顾客 | 小包或入门牌盒，轻松配色 | 同上 |
| 收藏家 | 收藏册/卡套，服装轮廓不同 | 同上 |
| 竞技玩家 | 牌盒/比赛包，利落装束 | 同上 |
| 路过顾客 | 日常服装，与店长区别明显 | 同上 |
| 熟客 | 具有可记忆发型或配件 | 同上 |
| 高预算顾客 | 收藏箱/特色外套，不能只加一个金色染色 | 同上 |

类型是视觉与行为标签，不强制绑定年龄或性别。至少七套基本角色；同类变体可共享身体结构，但不能只复用店长贴图染色。顾客画像由后端提供 `appearanceId`，前端按清单选图。

### 5.3 地图与物件

主店必须有：入口、零售货架、供应商/开包柜台、二级市场柜台、垃圾桶、通往对战房的门。零售柜台与单卡柜台应一眼能区分。

对战房必须有：出入口、少量双人牌桌、等候点、服务/报名点。首批先做两桌，资源支持后续扩展。桌面卡牌可抽象表现，不需要把原战斗界面微缩绘入地图。

至少交付：地板、墙、拐角、门窗、柜台、货架、封包/封盒陈列、垃圾桶、牌桌、椅子、灯具、招牌、地毯/装饰。家具应来自可组合瓦片或独立精灵，不只交付一张不可编辑的整店烘焙背景。

建议层次：地面 → 墙面/基础家具 → 按脚底 Y 排序的角色与遮挡物 → 家具顶部/前景 → 昼夜光层 → 提示。遮挡要以物件定义处理，不能整层柜台永远压住所有角色。

### 5.4 图集、清单与来源

`assets/frontend/manifest.json` 至少声明：

```json
  "characters": {
    "owner": {
      "sheet": "/assets/frontend/characters/owner.png",
      "portrait": "/assets/frontend/portraits/owner.png",
      "frameWidth": 24,

      "anchorPx": [12, 30],
      "directions": {"down": 0, "left": 1, "right": 2, "up": 3},

    "store": "/assets/frontend/maps/store.json",

```

相对路径统一按清单 URL 解析或使用上述根路径，不依赖机器绝对路径。缺少角色资源时展示明确的通用占位形象并记录错误，不用错角色掩盖缺图。

交付美术生成脚本、色板、源图/源工程、工具版本和素材来源说明。可以下载合法可用的绘图工具，但只在自己的工具目录记录安装/使用方式，不改根依赖，不让玩家安装美术工具。使用商业工具时不得把授权当成已具备条件。

优先验证代码驱动的可复现绘制流程：固定参数 → 生成基础像素图 → 图集检查 → 人工像素修整 → 保留源文件与导出命令。仅写工具名称、不交可用素材不算完成。

现有武将卡图继续复用，只读使用后端给出的 URL；不要求重画 2563 张卡面。场景角色像素画与武将原卡图可以使用不同表现形式，但卡框和 UI 需统一。

## 6. 地图、移动、寻路与 NPC 的责任划分

### 6.1 地图数据

前端负责美术地图与碰撞/导航数据，主模型负责加载并校验这些数据，以同一版本提供权威移动、交互距离和 NPC 路线。不要双方各画一套碰撞坐标。

地图 JSON 至少包含：`mapId`、`navVersion`、`tileSize`、宽高、图层、可通行格、碰撞多边形或矩形、入口/出生点、出口、交互点、排队点、桌位与座位锚点。

核心语义 ID 固定：

| ID | 语义 |
| --- | --- |
| `store.entry` | 主店入口/出生点 |
| `store.retail` | 密封商品陈列与零售管理 |
| `store.counter` | 进货、收货、拆盒、开包 |
| `store.secondaryMarket` | 二级市场单卡交易 |
| `store.trash` | 丢弃与捡回 |
| `store.toBattleRoom` | 去对战房的门 |
| `battleRoom.toStore` | 返回主店 |
| `battleRoom.service` | 报名、桌位与费用 |
| `battleRoom.table.01` / `.02` | 首批两张桌子 |

交互点要分开声明家具占地、玩家站位、交互距离和视觉标签点；不能把家具中心当作可走的目的地。所有位置使用地图原生像素，禁止混入 CSS 屏幕坐标。

门与桌位关系也在数据中声明。主模型消费地图元数据时将检查出生点可走、交互站位可达、出口双向匹配、座位不重叠、地图版本一致。前端交付以后如更改导航，必须同步提交对应地图并写明 `navVersion`。

### 6.2 行走与输入

- 四方向各有独立朝向，待机保留最后朝向，走路帧跟实际位移距离推进。
- 有速度变化时动画同步，不把固定上下晃动当行走；被墙挡住时停止迈步。
- 支持 WASD/方向键、E 交互、B 背包、Esc 关闭最上层窗口、点击地面寻路。
- 第一阶段建议四向走格/连续四向移动；若支持斜移，速度必须归一化，朝向规则固定。
- 点击家具先走到可达交互点，到达后请求交互；用户按方向键可取消自动寻路。
- 失焦、打开面板、触屏 pointercancel 后清除按键，避免卡住持续移动。
- 不自动吞掉输入框的方向键、空格与字母；面板打开时地图不响应移动。
- 家具、门、NPC 遮挡与相机滚动不会导致屏幕点击位置偏移。

### 6.3 后端移动与视觉插值

正式模式通过 Host 的 `world.input` 发送移动意图，后端返回权威 actor 位置、朝向、路径阶段和 `navVersion`。前端做平滑显示与行走帧，不自行生成 NPC，也不在“走到收银台”回调里确认销售。

玩家短时间预测可改善手感，收到权威位置后平滑纠正；明显越界立即校正。不要逐像素向业务命令发请求，也不要每帧写存档。

NPC 购买、开包、等候、入座、退场由后端状态机控制。前端根据 `activity`、位置与短提示展示，不依靠动画计时器改变经济状态。动画完成事件只用于展示或确认视觉完成，不能成为付款与奖励的唯一依据。

Mock 可以模拟位置和活动来演示，但代码必须放在 `frontend/mock/`，正式页面不得调用它驱动经营。

## 7. 页面结构与交互细节

### 7.1 总布局

桌面优先适配 1366×768 与 1920×1080：顶部简洁 HUD，主体为像素场景，旁侧可收起店主手账；不再让长表格永远挤压地图。

HUD：营业日、时间、暂停原因、营业状态、游戏币、欠款提醒、背包、任务、存档、手册。资金使用“游戏币/金币”语义，不增加真实支付入口。业务数据、格式化货币单位由 Host 指定。

窄屏把手账折叠，面板可全屏；保持按钮能点、详情能滚动。场景按整数倍显示，空间不足时用原生分辨率视口或相机裁切，不用任意非整数拉伸糊掉像素。

### 7.2 窗口管理与暂停

所有交互都通过统一窗口管理器：打开时申请 Host 暂停令牌，确认成功再允许提交业务操作；关闭时释放自己的令牌。

- 背包 → 详情 → 确认框是嵌套窗口，关闭详情不能恢复背包背后的时间。
- 手动暂停、失焦暂停和玩家对战暂停由 Host 独立管理，前端不得通过关窗强行取消。
- 暂停期间允许按钮反馈、翻页、开包动画和玩家战斗，NPC 行走与购物、配送、桌位计时停止。
- 打开过程出现连接错误时立即锁住地图输入与提交按钮，显示重试，不放任世界继续跑。
- 释放失败由 Host 保留并恢复会话状态；UI 不自行把时钟改成运行。
- 窗口销毁、路由切换和异常都要清理订阅、计时器及所属令牌；仍在后台的页面保持后台暂停原因。

HUD 从 Host 显示暂停状态，例如“暂停 · 查看背包”，不是前端自己用系统时间计算营业分钟。

### 7.3 背包与收藏

- 同卡显示 `×数量`，稀有度 N/R/SR/SSR、名称、可交易数、保留/参赛/挂单状态清晰。
- 提供名称搜索、稀有度筛选、持有/重复/在售筛选与排序。后端负责完整目录查询，UI 负责输入与列表呈现。
- 点击卡图打开详情；不在背包直接出现正店单卡货架入口。
- “留一，其余上架”先请求预览，显示保留、锁定、已在售和本次新增数量，确认后执行。
- 无库存、无匹配、加载中、加载失败、操作中有独立状态，不把失败显示成空列表。
- 大图懒加载，列表分页或虚拟化；不能为 2563 张牌一次请求所有卡图与技能源码。

### 7.4 卡牌详情

显示：卡图、名称、势力/版本、印刷稀有度、当前全局评分/分级、技能、持有与保护、市场资格、当前参考价、分模式战绩与有效样本量。

“印刷稀有度”与“当前全局分级”可能因后续评分版本变化而不同。前端同时展示后端提供的两个字段，不擅自覆盖卡框。

技能原文与源码通过延迟查询加载，源码默认折叠。文本按纯文本或经过约定渲染器的结构显示，不 `eval` 技能代码，不直接把未处理 HTML 注入页面。

样本不足显示“实战样本不足”；不能把评分 78 显示成 78% 胜率，也不能拿初估可信等级冒充统计置信区间。不能参赛时显示 Host 的具体原因及相关引导，不出现“本期专用将池”文案。

### 7.5 进货、签收、包/盒零售

- 供应商页显示主题、商品规格、当前新版本、进价/建议售价、出货说明、有效报价与送达条件。
- 散包显示每槽/每包的稀有度概率、至少 R+ 小保底；卡盒显示固定四档张数与整盒大保底。
- 概率单位写清楚：“每包至少 1 张 SSR 的概率”不等于“单张 SSR 概率”。后端分别提供，不自行相乘推导。
- 下单使用 quoteId，确认数量、金额、信用条件；新价格发布时已接受订单不改价。
- 配比变动展示当前版/上一版、变化原因和生效时间；不显示或泄露具体盒序和隐藏卡内容。
- 已签收仓库、已拆盒余包、零售货架与待签收订单分区，不把未到货商品当作可开库存。
- 正店货架只允许密封包/盒，单卡操作引导至二级市场。

### 7.6 开包与批量汇总

- 单包动画依次揭牌，可点卡查看技能；所有结果由 Host 返回的 operationId 与结果决定。
- 一键开包先选择范围、是否包含密封整盒、是否跳过普通动画，再展示后端预览。
- 支持“逐张展示 / 只看 SR+ / 直接汇总”，切换展示不重新调用开包命令。
- 结果按武将、印刷版/稀有度汇总，显示新增、重复、数量和高稀有度；可继续“留一上架”。
- 取消展示只关闭动画，已提交的开包不能通过取消把包退回来或重抽。
- 未收到命令结果时显示“确认开包结果中”；断线后按同一操作 ID 查询，不能生成新请求再次扣包。

### 7.7 二级市场

至少分“买卡 / 我的出售 / 收购报价 / 行情记录”。店主自营和 NPC 寄售标签不同，挂单不等于成交。

- 买卖均显示单价、数量、费用、预计净额、库存与锁定信息。
- 报价过期或库存变化显示后端最新报价，要求重新确认，不静默以更贵价格成交。
- 收藏、竞技、缺卡等 NPC 需求可用简短标签展示；别把全部内部估值公式堆进主要流程。
- 价格详情可展开：全局评分、样本量、战绩影响、供需、版本溢价、最近变化。
- “已进入市场”与“当前拥有”是不同状态；不要因卡种可参赛就在 NPC 手里画出无限副本。
- 无真实买家时挂单保持未成交，Mock 展示也需标明演示，不把挂单价当作到账现金。

### 7.8 对战房、配队与下注

- 桌位展示空闲、等待对手、进行中、待结算、异常待恢复；可按 Host 允许动作操作。
- KOF 三个位置固定次序；BO3 单将。可用阵容来自后端，展示缺卡、未流通、锁定、技能故障原因。
- 确认页显示双方稀有度、模式、NPC 提议倍数、基础注、最终注、开桌费、抽水规则和可用余额。
- 倍数来自 Host；前端只展示理由和接受/拒绝/降注入口，不从卡框等级自行计算赔率。
- 可以无赌注对战；店长亲自参赛的费用按 Host 返回规则显示。
- 比赛主视图为原引擎挂载区，工具栏由前端提供；牌局内部 UI 和结算验证由主模型负责。
- 败局、本局/整场认输、BO3 下一局与返回店铺分别说明，防止把返回误当退款。
- 断线、失败、重复点击等错误都经 Host 处理，UI 不直接发奖金或解除参赛锁定。

### 7.9 任务、日报、垃圾桶与存档

- 任务有可追踪引导：进货柜台、零售区、二级市场、对战房、垃圾桶。路径由场景路由与 Host 可交互状态共同决定。
- 日报将商品销售、服务收入、参赛净盈亏、费用、托管资金分开；未售卡估值不计收入。
- 垃圾桶支持单张和全部捡回，明确“开始下一天清空”；展示锁定物品不可丢弃的原因。
- 按天存档显示日期、分支、时间、来源类型与可读状态；保存、导入、导出、读取均调用 Host。
- 不在前端恢复原始存档 JSON，不自行清 IDB。旧档已获准废弃，新开发档仍需要完整日存档功能。
- 旧档重置是主模型的一次性开发动作，不作为每次刷新前端就自动运行的逻辑。

### 7.10 保留现有经营入口

新版不能因为重做外观就丢失已有功能：设施升级、员工、街坊对话、预约交付、收卡申请和规则编辑器应保留可达入口。

- 设施/员工页展示后端返回的等级、下一档费用、每日工资、效果、解锁条件与可执行动作，不在 UI 累加属性。
- 街坊页展示关系、头像、对话、报价与预约；接单、交付、拒绝分别调用命令。
- 编辑器放入独立的设置/开发区域，普通玩家主流程不展示模块内部结构。JSON 草稿只是 UI 状态，提交必须经 Host 校验，失败不改正式配置。
- 设置包含音量/动画/显示缩放等前端偏好；营业速度、规则配置等业务参数仍走 Host。
- 导入文件先校验格式与能力，不执行文件中的脚本；需要重启或新世界的配置明确提示，由主模型定义应用策略。

如果某项真实功能的新版 Host 尚未提供，前端先做好禁用/未接入状态与 Mock 展示，并在接口缺口记录，不能删除入口或直接调用旧全局函数绕过接口。

## 8. 全局评分、四档稀有度与动态产品：前端必须理解的规则

这是用户新增的核心规则。**计算与数据生成全部归主模型，前端负责正确展示和交互。**

### 8.1 全卡统一评分

流程固定：

```text
全目录武将技能与属性
  → 统一评分模型（牌差、伤害、生存、控制、条件、代价等）
  → 每位武将的 KOF/BO3 评分与全局综合分
  → 全局同一组 N/R/SR/SSR 分数界线
  → 每个主题实际包含的四档卡种分布
  → 该主题新版散包配方 / 整盒定额 / 采购与零售报价
```

同一技能版本的武将放在不同主题里，分数和分级相同。某主题最强的一张也可能只有 R，另一个主题则可能拥有多张 SSR。不能为了凑齐某包四档而给它单独升档。

全局评分不是单包内部排名；也不是武将来源、称号、神势力或技能字数。当前目录约 2563 位，很多评分仍是低可信初估；界面必须保留校准状态，不假装所有武将已实测。

数值阈值、模式权重、技能评价和复核策略由主模型确定与版本化。本交接文档不授权前端重评卡牌。新档只使用四档，不需要为旧 C/U/UR 编写兼容 UI。

### 8.2 动态配比的真实含义

不同主题的卡池组成不同，新产品配比随全局分级变化而变化；不是所有主题一直套同一个固定商品档配方。后端可以使用稀有度卡种数量、强度分布、稀缺权重、目标商品价值与保底约束求出配方。

前端收到的是确定结果：

- 全局评分版本 `ratingVersion`。
- 主题真实卡种分布 `poolSummary`，含四档数量和评分摘要。
- 散包槽位与边际分布、小保底说明。
- 整盒固定四档数量、包数、每包张数与大保底。
- 缺档处理或停供原因、是否使用补位、补位卡池范围。
- 商品版本、价格版本、生效时点与当前报价。

**卡种占比不等于抽到该档的概率。** 比如主题里 SSR 卡种占 10%，不表示每包有 10% SSR，也不表示每张有 10% SSR；配方与槽位仍需后端根据经济目标和保底计算。

抽卡候选池不受“已经进入二级市场”的对战准入记录限制，否则新卡永远无法开出来。流通限制只作用于参战准入，抽包负责把新卡引入世界。

缺档时由主模型选择同档补位、调整商品或暂停该产品；前端必须展示实际结果。若承诺每盒至少一张 SSR，而该主题无 SSR，就必须有明确的同档补位或不能发行该版，不能偷偷给 R 换标签。

### 8.3 动态仍然要遵守整盒固定配额

动态发生在**发行/供货版本生成时**，不是玩家每开一包就改变旧盒内容。

示意：

| 示例商品 | 盒规格 | N/R/SR/SSR 固定张数 | 说明 |
| --- | --- | --- | --- |
| 某主题 A 版 | 24×5=120 | 84/30/5/1 | 老版已生成盒继续使用该配额 |
| 同主题 B 版 | 24×5=120 | 72/38/8/2 | 评分/供给变化后新生成的产品版 |

这是 UI 演示用的可行数字，不是最终平衡参数。每版都需要同时满足 120 张总量、整盒定额、每包 R+ 小保底和 SSR 大保底。后端负责可行性验证和整数配盒，前端不做随机塞卡再补保底。

同一版本盒拆出的余包保留来源；剩余包的条件概率与原盒承诺不同。前端可以显示公开的已开统计和剩余数量，不读取或泄露后台隐藏顺序。

### 8.4 动态价格与数据边界

建议后端同时处理配方与报价，避免分别更新造成“配比已变、价格还是旧的”。新供货版本内的预期卡值、采购价与建议售价一起发布。

```text
新版包基准价值 = Σ（配方的各档平均张数 × 当期发行卡值）
新版盒基准价值 = Σ（各档固定张数 × 当期发行卡值）
采购/建议售价 = 根据基准价值、供给、拆包回报目标与毛利目标生成
```

当期发行卡值由后端对全局强度、稀有度与已验证行情作有界处理，不直接把某张天价挂单代入所有卡包。实战胜率用于二级市场价格，影响新产品估值时还要防止小样本与重复倒手推价。

UI 不按这几行公式重新计算金额，只展示后端提供的解释与结果。正式金额使用整数最小单位，不能用浮点相加收款。

- 评分/供货按固定时点发布，默认可按日，不随前端渲染频率改变。
- 下单冻结 quoteId、产品版、配方、数量和总价；既有实体内容不重抽。
- 当前目录分级可能更新，已有印刷卡保留生成时的稀有度，详情并列显示当前分级。
- 密封商品成本与采购合同不被重新估价覆盖；建议售价变化和实际历史成本是两件事。
- 新档清空只免去旧版迁移，不免去新档内部后续版本的快照与守恒。

## 9. Host 接口契约 v1.0

以下方法和数据是**双方后续按其实现的协作规格**，不是当前服务器已经提供的 API。不要自行请求不存在的 `/api/market` 等地址。

### 9.1 基础方法

```ts
interface CardShopHost {
  connect(input: {
    contractVersion: "card-shop-ui/1.0";
    clientId: string;
  }): Promise<ConnectResult>;

  query<T>(name: string, input?: unknown): Promise<QueryResult<T>>;
  command<T>(input: CommandRequest): Promise<CommandResult<T>>;
  subscribe(listener: (event: HostEvent) => void): () => void;

  pause: {
    acquire(input: { ownerId: string; reason: string }): Promise<PauseLease>;
    release(leaseId: string): Promise<void>;
  };

  world: {
    input(input: WorldInput): void;
  };

  battle: {
    mount(input: { container: HTMLElement; matchId: string }): Promise<{
      dispose(): void;
    }>;
  };

  disconnect(): Promise<void>;
}

type QueryResult<T> =
  | { ok: true; revision: number; data: T }
  | { ok: false; error: HostError };

type CommandRequest = {
  requestId: string;
  type: string;
  payload: unknown;
  quoteId?: string;
  previewId?: string;
};

type CommandResult<T> =
  | { ok: true; requestId: string; revision: number; data: T }
  | { ok: false; requestId: string; error: HostError };

type HostError = {
  code: string;
  message: string;
  retryable: boolean;
  details?: unknown;
};

type PauseLease = { leaseId: string; ownerId: string; reason: string };
```

`connect` 返回 `contractVersion`、`worldId`、`branchId`、`sessionId`、`revision`、`currency`、`capabilities`、`initialSnapshot`。契约版本不支持时阻止提交。`currency` 至少含 `code/label/minorUnit`；金额统一使用非负安全整数，亏损汇总等允许带符号字段另行声明。

查询返回只读 DTO，不暴露可直接修改的正式 save 对象。前端可更新本地缓存视图，但不能把缓存当作账本。Host 返回的 `revision` 是同步游标，不要求每次营业 tick 后所有报价都失效；报价使用独立版本和失效条件。

### 9.2 请求与结果

- 每次新的用户意图生成一个 `requestId`；网络重试复用原 ID。已确认的失败若用户改了参数，应生成新 ID。
- 后端按世界、会话/主体和请求 ID 去重；成功响应丢失后重复提交返回原结果，不二次扣款。
- 多次点击同一按钮时置 pending；不要靠按钮禁用替代后端幂等。
- 断线或超时属于“结果未知”，先用 `operations.get` 查询，再按同一 ID 重试，不直接告诉玩家“失败且未扣款”。
- 有业务预览的操作使用 `previewId`，有报价的使用 `quoteId`。预览与报价失效时后端拒绝并要求重新确认。
- `quoteId` 和 `previewId` 统一放在 CommandRequest 顶层；下表提到它们时也是指顶层凭证，不在 payload 内再复制一份。实体引用、数量等业务参数放 payload。
- 错误如 `INSUFFICIENT_FUNDS`、`OUT_OF_STOCK`、`QUOTE_EXPIRED`、`PREVIEW_EXPIRED`、`ITEM_LOCKED`、`NOT_IN_RANGE`、`NOT_ELIGIBLE`、`ENGINE_UNAVAILABLE`、`WORLD_RESET`、`CONTRACT_MISMATCH` 使用统一错误组件。
- `error.message` 面向玩家；调试栈与原始状态不直接展示给玩家。

### 9.5 关键 DTO

以下是必须保持含义一致的最小字段。可由主模型补充，不得把它们替换成 UI 内推导值。

```ts
type Rarity = "N" | "R" | "SR" | "SSR";
type CardKey = string; // 不透明业务 ID；禁止从中文名或文件名推导

type CardSummary = {
  cardKey: CardKey;
  generalId: string;
  skillVersion: string;
  name: string;
  imageUrl: string;
  currentRarity: Rarity;
  globalScore: number | null;
  ratingVersion: string;
  reviewStatus: "calibrated" | "estimated" | "needs-review";
};

type InventoryRow = {
  inventoryRef: string; // 可指向单张或可追踪批次，不由 UI 解码
  cardKey: CardKey;
  printVersion: string;
  printedRarity: Rarity;
  location: string;
  owned: number;
  available: number;
  protected: number;
  locked: number;
  listed: number;
  eligible: boolean;
  disabledReasons: Array<{code: string; message: string}>;
};

type ProductSummary = {
  productId: string;
  themeId: string;
  productVersion: string;
  ratingVersion: string;
  priceVersion: string;
  cardsPerPack: number;
  packsPerBox: number;
  poolSummary: Record<Rarity, number>;
  boxCounts: Record<Rarity, number>;
  packExpectedCounts: Record<Rarity, number>;
  packAtLeastOneProbabilities: Record<Rarity, number>;
  guarantees: string[];
  substitutionSummary: string | null;
  availability: "available" | "unavailable";
  unavailableReason: string | null;
};

type Quote = {
  quoteId: string;
  productVersion?: string;
  priceVersion: string;
  quantity: number;
  unitAmount: number;
  subtotal: number;
  feeAmount: number;
  totalDebit: number;
  totalCredit: number;
  validUntil: {day: number; minute: number} | null;
  explanation: string[];
};

type ShopSnapshot = {
  worldId: string;
  branchId: string;
  revision: number;
  clock: {
    day: number;
    minute: number; // 当天 0～1439 的游戏分钟
    phase: "preparing" | "open" | "closing" | "closed";
    speed: number;
    running: boolean;
    pauseReasons: Array<{code: string; label: string}>;
  };
  wallet: {
    available: number;
    debt: number;
    escrowLiability: number;
  };
  allowedActions: string[];
};
```

概率为 0～1，计数为非负整数，预期张数可为小数。`packAtLeastOneProbabilities.SSR` 表示每包至少一张 SSR 的概率；`packExpectedCounts.SSR` 是平均张数，二者不得混用。需要 R+ 概率或槽位说明时由 Host 另给字段，UI 不按独立假设拼装。

库存 `protected/locked/listed` 是各维度说明，可能有重叠，**不可简单用 owned 减去三者求 available**；以 Host 的 `available` 为准。Quote 买卖方向通过请求上下文确定，实际付款/到账使用 totalDebit/totalCredit，不猜测费用符号。

### 9.6 快照事件、移动与战斗挂载

`HostEvent` 统一带 `contractVersion/worldId/branchId/seq/revision/type/data`。最低事件：`snapshotUpdated`、`actorsUpdated`、`operationUpdated`、`notification`、`battleStatusChanged`、`worldReset`、`connectionChanged`。

- 前端发现 seq 缺口或世界/分支改变，重新读取快照；不能拿新分支事件覆盖旧缓存。
- 启动先 connect 获取初始快照，再订阅；正式 Host 应缓冲连接至订阅之间的更新，或提供可重同步机制，不能悄悄漏事件。
- `actorsUpdated` 包含 actorId、appearanceId、roomId、x/y、方向、moving、activity、受控短文本、navVersion。
- `WorldInput` 包含 sessionId、单调递增 inputSeq、roomId、navVersion、按键方向或点击目的地；失焦、关窗与断开时发送 stop。输入与业务命令使用不同通道。
- 输入可按约 10～15Hz 合并发送；视觉绘制独立于该频率，主模型最终控制移动校验和保存。
- 正式 `battle.mount` 由主模型管理 iframe 创建、运行地址、加载、origin/source 校验和结果消息。前端只提供空容器与工具栏，不直接发送 engine postMessage。
- Mock 的 battle.mount 只显示“战斗占位预览”，如需演示结果使用 Mock 专用控制，不能伪装为实际引擎对战。

Host 的逻辑时钟独立于前端动画帧。Phaser 的 `update` 不调用旧 `BusinessUI.tick`；前端停止渲染、切场景或打开窗口都不能制造第二个经营时钟。双方订阅通过 sessionId 区分，主模型在会话失联时暂停受控世界并等待恢复，不因为一个过期的短租约让阅读中的页面突然继续营业。

### 9.7 新世界与旧档重置

用户已授权废弃旧档，但本轮只写规范，不实际删除。

主模型后续执行重置时，仅处理本游戏明确命名的正式存档、日档与配置覆盖，建立新版 schema/worldId；范围要可核对，不清空其他站点/应用数据，不删除引擎或资源。新档初始化成功后发布 `worldReset`，前端清理该世界的视图缓存和选择，重新连接。

前端 Mock 默认只用内存；若保存布局偏好，键统一加 `noname-card-shop-frontend-preview:` 前缀。不得触碰原 `noname-packer-v1`、日档数据库或桌面正式用户目录。

旧档无需迁移，但新档内按天读档、分支与后续产品版本仍需正确处理。开发素材预览刷新不应清空真实新档。

## 10. 独立运行、Mock 与联调

### 10.1 当前可用的启动方式

在项目根目录执行 `npm run dev:open`，或双击 `开发启动.cmd`；现有开发服务使用 `http://127.0.0.1:5190/`，引擎 5191。前端目录创建后可打开：

```text
http://127.0.0.1:5190/frontend/index.html?mode=mock&fixture=store-day
```

当前静态服务能按文件提供 `/frontend/` 和 `/assets/frontend/`，但**现有自动监视只覆盖旧入口，未覆盖新前端目录，也不会自动向该入口注入开发脚本**。独立开发先手动刷新，不要自行修改 `dev/runtime.mjs`；最终由主模型扩展监视与入口。

不要用 `file://` 双击 HTML 作为联调方式。根依赖若缺失，沿用已有初始化流程；不要运行发布、打包或清档命令来解决前端预览问题。

### 10.2 Mock 场景清单

Mock 只用于布局、状态与流程演示。固定数据和固定种子，不能写正式业务存储。至少提供：

| fixture | 应覆盖内容 |
| --- | --- |
| `store-day` | 白天主店、不同类型 NPC、正常库存与 HUD |
| `store-evening` | 黄昏/夜晚、灯光、关店状态 |
| `inventory-many` | 2563 条元数据或等量虚拟记录、重复卡、分页与搜索 |
| `opening-summary` | 新增/重复/SSR、大量开包汇总与详情返回 |
| `market-empty` / `market-active` | 空市场、在售/寄售、报价与费用 |
| `product-revision` | 两个供货版本、配比和价格变化、旧订单冻结 |
| `battle-room` | 两桌不同状态、NPC 入座、配队与倍数提议 |
| `locked-items` | 收藏/参赛/挂单重叠，available 不等于简单相减 |
| `errors` | 连接失败、图片失败、报价过期、重复点击、提交结果未知 |
| `save-branches` | 日档列表、分支、读取前确认、worldReset |

每个命令的 Mock 响应结构与正式契约一致。允许在 Mock 中确定性更新演示库存和钱包，但不能引入另一套平衡算法；“交易成功”仅代表页面流程演示通过，不代表正式经济和引擎验收通过。

### 10.3 前端自验收

- 主店到对战房再返回，位置与朝向正确，无门口死循环。
- 所有角色至少四向行走；不同类型不只是店长换色。
- 不同窗口嵌套下，暂停令牌申请/释放成对；手动暂停不被清除。
- 包/盒零售、单卡市场入口和内容正确分开。
- 批量开包预览、提交、汇总、详情、留一上架流程完整；重试使用同一请求 ID。
- 产品配比、报价和当前评分全部来自 Host，不因 UI 筛选或刷新自行变动。
- 新旧供货版并列时不改旧订单；卡种比例、每张概率、每包概率和盒定额没有混淆。
- 在售不显示为已到账；赌注本金不显示为经营收入。
- 正式 Host 缺失会报错，不自动切 Mock。
- 宽屏/窄屏、键盘/鼠标/触屏、失焦/异常/缺图均可操作。
- 允许目录以外无任何改动；无正式 localStorage/IndexedDB 写入；无根依赖变更。

### 10.4 性能与资源检查

默认用两间房、最多 12 个可见角色作为首批样板负载，目标为开发电脑桌面浏览器接近 60fps；记录实际设备、窗口尺寸和测量结果，不空称性能达标。

- 列表只渲染当前页或可见项，卡图懒加载，技能源码按需获取。
- 不每帧重建整个 DOM，不每次光照变化重绘所有素材文件。
- Map/精灵切换后销毁旧事件和纹理引用；同一资源复用缓存。
- 记录首屏资源总量、最大纹理、缺图/缺帧检查结果；大资源拆分加载。
- 资源检查脚本验证图集尺寸整除、帧索引、透明底、清单路径、地图交互可达与出口匹配。
- 不把 1.3GB 无名杀原包复制进新 `frontend/`；只引用所需本地资源。

## 11. 并行协作与最终合并流程

### 11.1 前端开发期间

5. 把接口缺口与视觉已完成功能分开报告，不能以 Mock 成功宣称后端已可用。

最终由主模型执行：

1. 检查差异只涉及允许范围，确认素材和接口没有暗含业务副作用。
2. 实现/核对正式契约、评分与动态产品规则、时钟、库存、NPC、市场、托管和存档。
