## 需要交付的三个场景

### 1. 一天的经营看板

用当前库存/采购概念设计“今天缺什么”和“昨天发生什么”：在库、在架、在途、近期销量、缺货次数、成交数、实际毛利、采购现金流。不要把采购支出全部算利润损失，不把挂单总额显示为收入。

日报先给一个可执行建议，例如“标准散包昨天缺货，补到可卖半天的库存”，再提供明细。建议数据只做有标注的静态样例，建议算法和权威值由主模型实现。

### 2. 顾客状态与店内动线

画出入店、浏览、排队、结账、拆包、弃牌/拾牌、去打牌和离店的路线与停留区。门口留作通行，不把全部等待位置放在同一点；垃圾桶、开包点和队列不占出口。

头顶保留适度大小的“姓名 + 类别”，状态可以用第二层短词或小图标，避免四五行长文字叠在角色上。繁忙时哪些标签简化、选中时如何看完整信息，需要说明。

缺货、买不起、价格不合适、排队过久和无空桌的提示要能区分，既有短反馈也有日报统计。不要把它们全部归结成一个“满意度低”。角色外观不能绑定贫富或消费能力。

设施可提交图形/标牌候选与占地建议，但寻路格和容纳人数由主模型决定。新场景比例仍按现有 16 像素格与世界尺寸标注，不靠随意缩小人物解决拥堵。

### 3. 牌桌状态

在营业 HUD/桌面标牌中表达：准备入座、正在打第几小局、BO3/KOF 比分、刚结束、技术中断和需要恢复。

所有交互暂停世界的要求继续有效：打开交互面板后明确显示“因交互暂停，关窗后继续”，不能一边暂停引擎一边让 UI 显示“卡住了”。普通营业 HUD 可被动展示最新状态，不新增暗中取消暂停的按钮。

技术中断与正常完赛的视觉、文案和统计分开；不得设计“随便判一个赢”作为解除桌位的方法。可设计查看原因和请求安全处理的入口，但必须标注需要后端支持。
