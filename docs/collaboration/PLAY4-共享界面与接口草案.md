# PLAY4：共享界面与接口草案

配套 [总分工](2026-10-24-窗口与牌桌新版分工.md)。运行代码基线 `0bbba5ad`。**以下是开发合同草案，不是已存在的 Host API。** 正式命令、DTO、默认数值和错误由主模型实现并同步 `contracts/`；候选通过注入 actions 展示，不能直改后端或借伪接口宣称接通。

## A. 一件器具对应一个窗口

| 入口 / 当前 ID | 新窗口内容 | 不应同时混进来的操作 | 负责 |
| --- | --- | --- | --- |
| `store.counter` | 进货：商品、数量、总价、确认购买；完成后提示已入库 | 开包动画、单卡交易、全量经营报表 | FAST-06 候选，主模型绑定 |
| 仓库/背包入口 | 密封盒包库存、数量、送去货架/拆包台；显示实际可用件数 | 重复收货、远程越过站位开包 | FAST-06 候选；是否新增实体仓库入口由主模型接导航 |
| `store.opening` | 拆包：选库存与数量 → 一次确认 → 卡面结果分页 | 下采购单、收银、单卡挂单 | FAST-06 候选 |
| `store.retail` | 零售货架：卡包/卡盒上架、售价、余量、撤下 | 单卡二级市场 | 主模型复用改造，FAST-05给布局/文案 |
| `store.checkout` | 顾客收银：当前结账状态与最近成交；保留已有自动收银 | 货架补货、采购、拆包；不新增每单必须手动确认的流程 | 主模型绑定，FAST-05给布局/字段缺口 |
| `store.secondaryMarket` | 单卡市场：买入/出售，卡面、实际持有、数量与价格 | 密封商品采购 | 主模型复用改造 |
| `store.trash` | 垃圾桶：丢卡/捡回，明确数量、来源与次日清空 | 交易报价、自动出售 | 主模型复用改造 |
| `battleRoom.service` | 报名台：牌桌大厅、桌费设置、当前候战情况 | 采购与市场、全量技能源码 | FAST-07 候选，主模型绑定 |
| `battleRoom.table.01/02` 等实际 `tableId` | 当前牌桌的报名/对局窗口：赛制、费用、对手/等待、打开选将 | 自动切成另一桌或重复大厅全量清单 | FAST-07 候选，主模型绑定 |
| 选将按钮 | 独立选将窗口；选齐当前赛制人数后一次确认 | 每点一张就关闭、重新弹窗或提交参赛 | FAST-07 候选 |

其余实际交互点由 FAST-05 从地图清单补齐。门/房间出口继续移动切换，不为“每件器具独立窗口”额外弹门窗；不存在的仓库实体不能在候选里假装地图已增加。

常规路径：进货（确认一次）→ 提示已入库 → 关闭后自由行动；可选“去仓库/去拆包台”导航。仓库不因为采购完成自动再强弹一次，转场由主模型处理原窗口关闭与暂停交接。

## B. 固定页面与适配要求

1. 每窗保持固定标题、主内容区和底部动作区，列表/技能长文/结果使用分页；不以长滚动列表、横向滚条、窗口内外双滚条完成玩家流程。不能只 `overflow:hidden` 把剩余内容截掉。
2. 标准验收：1440×900、1366×768、1280×720、1024×768、406×1000。浏览器缩放100%；放大字体时应降低每页容量/切换信息页，仍能到达确认和关闭。1280×720优先保证主操作。
3. 选将桌面初始建议每页 **8张（4×2）**，紧凑屏6张（3×2），窄屏4张（2×2）；采购建议4～6个商品/页，开包结果建议8张/页。以实际可用窗口高度校验后由主模型定最终容量。大小变化按卡牌ID保持选择，不能因索引改变选错卡。
4. FAST-04 的48张是性能上限的旧实现，本轮必须满足不滚动的新要求，不能直接照搬48张塞入固定高度。大库存仍全量可搜索/翻页，不能只取接口第一页或全量挂载隐藏 DOM。
5. 卡面保留约3:4比例，优先 `object-fit:contain`；实体像素素材不重新采样重画。正文建议14～16px，辅助文字不小于12px；按钮桌面至少36px高，窄屏触控目标建议44px。不给未知数值填0。
6. 当前页号、总数、上一页/下一页和确认固定可达；较长列表支持页码跳转和搜索，避免连点上百次。搜索/筛选回第一页，已选阵容保留。0条、1页、尾页、超长名称/技能、无图、加载、失败、空余额、结果未知均有明确状态。
7. 长技能正文可分页或选择技能页，完整文本必须可达。技能源码属于独立开发/高级查看入口，不占玩家确认页；不擅自删除原有查看能力。
8. 窗口管理器由主模型修改。候选不自行申请暂停令牌、不监听全局Esc、不改 `body` 滚动/键盘锁，也不创建第二套全局弹层系统。主模型负责焦点、Esc只关最上层、父窗草稿、重入和销毁。

## C. 文案规则

| 原措辞例子 | 玩家措辞方向 |
| --- | --- |
| Host、DTO、分支、实物引用、预览ID | 常规页不显示；必要时“进度已变化，请重新确认” |
| 获取整篮报价 / 确认整篮采购 | 明细标价并在“购买”时校验；有变化再提示，不默认多加一次询价按钮 |
| 一键签收全部已到货 | 新即时入库流程不显示；旧订单兼容另行处理 |
| 单包欣赏 / 整盒快开 / 全部散包 | 开一包 / 开一盒 / 全部打开（明确是否包含整盒） |
| 确认参赛（冻结阵容与托管） | 开始等待 / 开始对局，费用在按钮旁明确显示 |
| 请查询原操作结果 | 正在确认上次操作；动作“查看结果” |

这些是语义方向，FAST-05给逐条替换表。玩家必须知道数量、价格、卡牌是否被占用、操作是否成功；精简不能隐藏真实扣款、不可逆消耗或失败。

## D. 候选组件合同

候选统一按 `mountX({root, view, actions, draft = {}, layout})` 提供组件，返回 `update(nextView)`、`getDraft()`、`dispose()`。可以直接复用正式纯 DOM/卡图函数；CSS 用包前缀，不能修改公共样式。展示多个窗口的 demo 必须是分开根节点/独立示例，不回到统一交易台。

### FAST-06 输入与意图

- `view`：只读 world/branch身份、商品/价格/实际密封库存/开包结果、各器具可用状态、pending操作和错误。来源可对应现有 `products.list`、`inventory.sealedSummary`、`opening.preview`；结果字段在 gaps 逐项映射，不随意改变单位。
- `actions` 提议：`purchase({lines})`、`goToWarehouse()`、`goToOpening(scope)`、`goToRetail(scope)`、`openPacks(scope)`、`checkLastOperation()`；这是 UI 意图，不是新增的同名 Host 命令。
- 新订购预计响应包含 `fulfillment:'received'` 与真实库存引用/汇总；当前正式 `supplier.placeBasketOrder` 返回 pending订单，主模型要修改后才成立。fixture响应必须标为拟定。
- 不直接在前端创建库存、抽随机数、分配保底、计算最终报价、自动重复提交或发新档礼包。拆包确认一次，由主模型内部取冻结预览并提交；预览不泄露未开卡内容。

### FAST-07 输入与意图

- 大厅 `view`：`tables`、当前 `tableFee`/允许范围、`queue`、`match`、模式、可执行动作和不可用原因。费用和状态只读；设置费用的 action 是表达意图。
- 选将 `view`：`mode`、`slots`、`items`、`favoriteCardKeys`、当前有序 `selectedRefs`。卡项至少包括 `inventoryRef/cardKey/generalId/name/imageUrl/rarity/eligible/reasons`；技能可经 `loadCardDetail({cardKey})` 按需读取，迟到返回须校验当前卡牌与组件生命周期。
- **现有 `combat.eligible` 不含 imageUrl、技能和收藏状态**；这属于主模型的兼容扩展任务，不能让候选用卡名拼图片URL或把稀有度当技能。
- `actions` 提议：`selectLineup({inventoryRefs})`（只把草稿交回父窗）、`setFavorite({cardKey,favorite})`、`setTableFee({amount})`、`joinQueue({tableId,mode,inventoryRefs})`、`leaveQueue()`、`setWaitMode({mode})`、`loadCardDetail({cardKey})`、`checkLastOperation()`。
- `setFavorite` 是明确设为true/false，便于重复请求幂等；不能用每次调用都翻转的toggle协议，也不能借 `inventory.setProtection` 实现。
- 玩家候战栏是地图上的小状态条，不是窗口管理器中的模态窗。提供等候状态、模式、当前阵容、取消、返回桌边、手动/自动移动切换；自动移动策略由主模型执行，组件不驱动坐标。
- 展示状态建议区分：未报名、等待、对手已就绪、载入中、进行中、等待下一局、整场结束、异常待处理。对应的正式状态机由主模型冻结，不能将当前prepared状态直接冒充已实现排队。

## E. 主模型必须冻结的语义

- 新采购的原子扣款/入库、旧pending/arrived订单兼容、赠品发放记录与日初快照顺序。
- 费用设置范围与版本、已接受价格的冻结、现金/预留/桌费收入区别、NPC预算和退出释放。
- 队列与真实match分离：排队时不要求已经找到对手；匹配、卡牌/桌位预留、离场与取消由同一权威状态协调，不在两个模块重复登记。
- 战斗暂停与普通窗口暂停的范围；NPC模拟不能因自己持有的经营暂停令牌永远停摆。30分钟跨打烊、任务到期、NPC行为、到期订单和多桌重叠的推进策略，失败/重试的持久标记。
- 正式比赛按可信引擎事件结束；仅UI显示胜负不结算。引擎事件来源、gameId/matchId、世界分支、结果去重和重新挂载安全性继续校验。
- 用户尚未提供的新评分规则需要数据来源、方法/版本、缺失值、样本/人工估计、BO3/KOF口径与例子；新价格/发行方案不得追溯改旧盒内容、历史成本、已付款订单或已接受费用。
