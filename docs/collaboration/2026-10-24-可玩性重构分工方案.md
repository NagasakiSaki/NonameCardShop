## 1. 共同目标

做成“能亲自走动、能收藏交易、能看见本地玩家圈成长的像素卡店”。先完成前三个营业日的连贯体验，再扩大内容量。

共同经营循环：看需求 → 备货与陈列 → 开门 → 顾客购买、拆包、交易或参赛 → 发现缺货与机会 → 收店总结 → 决定明天投资。

保留本项目独有的流通链：卖出密封商品 → NPC 拆包 → 留牌或弃牌 → 店长/部分顾客拾牌 → 持卡与市场变化 → 模拟比赛及需求变化。需要让玩家看懂自己的决定怎样影响它。

平价走量、收藏精品、对战社区是可渐渐形成的经营方向，不在开局强制选择职业，不做三套互斥存档和独立经济。

## 4. 主模型必须承担的工作

### CORE-PLAY-01：前三日的可玩循环

- 第一天：准备与采购、清楚的收货上架路径、第一笔销售、拆包和保留/出售取舍、第一次收店总结。
- 第二天：熟客带明确需求回访；玩家选择常规补货、收藏交易或改善一个经营瓶颈；可看到卖出/拾取的牌影响持卡。
- 第三天：一次可选的小规模店内活动，让既有模拟牌桌、商品需求和熟客发生联系，结束后给出下一步经营选择。
- 这不是硬编码三天脚本。用条件、事件、文案、奖励引用、完成记录等数据驱动；明确可重复/一次性、缺资源时的替代路径、跳过引导与旧档接入。
- 不锁住已有功能逼玩家按步骤走；任务不要求抽中特定稀有卡、不要求靠垃圾桶才能继续、不强制打真实牌局。
- 单日 8～12 分钟只作为初期节奏假设，指世界实际运行时间，不计交互暂停与可选真实对战；需试玩后再定，不直接改现有时钟。

### CORE-PLAY-02：可解释的顾客与交易

统一持久身份、访问意图、当前活动、未成交原因及统计口径。缺货、预算不足、定价不接受、排队超时、桌位满、路径异常分别处理；同一顾客可以多次遇到问题，但日报“最终未成交人数”不能重复加人。路径失败属于技术诊断，不能罚玩家声望。

熟客愿望与需求不能由外观、角色原作人设决定。角色外形与姓名、贫富、消费偏好保持分离。先完成少量可记住的熟客，不批量堆砌对话。

### CORE-PLAY-03：经济与成长

- 基础强度/稀有度、实际供应、个人缺卡与搭配需求分开；供货梯度保留，市场情绪不能偷偷重写旧盒内容与印刷稀有度。
- 胜率相关价格使用样本置信度、时间窗口或衰减、涨跌边界；真实/模拟来源保留区别。不能靠小样本循环把价格推到无限。
- 检查拆包期望、整盒保底、NPC 预算、免费拾牌、自动奖励、牌桌费和库存成本的联动。保留用户要求的高奖励，优先调整目标和经营选择，任何大幅数值改变都单独列明。
- 设施升级逐步有可见效果：展示、活动、服务和自动补货；先核对真实效果，不靠面板承诺不存在的功能。工资、赊购、预留、到账、已售成本、库存估值分别计算。

### CORE-PLAY-04：接口、恢复与合并

主模型维护 `contracts/`、`modules/backend/`、正式数据配置、Host 适配、地图碰撞/站位、窗口暂停、入口和存档迁移。新统计应由真实事件产生，不让 UI 根据动画补账。

日初读档必须同步恢复新任务、事件、关系、访问、统计及随机状态；不能在重开窗口或重载页面时再次发奖、造故事、重复收桌费。旧档兼容，不为本轮设计自行清空用户存档。

## 5. 候选界面的共享约定

外部模型先交可交互的独立组件与 Mock 预览，不连接正式世界。现行真实协议是 `card-shop-ui/1.0`，新增展示模型没有自动成为 Host v2。

建议各包组件提供同样的本地挂载形式，**这只是候选组件接口，不是已实现的业务 API**：

```js
export function mount({ root, view, actions, assets }) {
  // 创建本组件自己的 DOM/样式，不改页面外其他节点。
  return {
    update(nextView) {}, // 接收新展示数据，保持合理焦点与滚动
    dispose() {},       // 可重复；清理监听、计时器和 DOM
  };
}
```

- `view` 是只读展示数据；缺失用“暂无数据/待提供”，0 与未知分开。不能编造行情和真实持有量。
- `actions` 由预览提供 Mock 回调，未来由主模型绑定真实行为。回调成功、失败、结果未知、旧分支失效均需有显示；候选不自行调用同名 Host 命令。
- A 的场景素材/地图示意不必采用此 DOM 组件形式；A 只需保证可加载、可对照、可复现。B/C 采用此形式便于最终接入。
- Mock 状态必须来自可切换 fixture；不能按现实计时器扣钱、推进顾客、产生比赛结果。允许界面动画，但动画不代表业务完成。
- 样式使用包内前缀或 Shadow DOM，不能写影响全站的 `body/button/*` 规则；资源路径相对模块解析，不依赖开发机盘符。
- 不用 localStorage/IndexedDB，不打开真实存档，不装全局依赖，不自行升级 Phaser 或 package。资源可以只读引用正式素材。
- 目前单卡交易仍在二级市场柜台、采购/签收在柜台、拆包在拆包台；菜单可快捷查看与寻路，不能凭 UI 按钮绕过站位。主模型确定合法快捷行为后再接。
- 所有正式交互保留暂停；被动 HUD 不申请暂停。多重暂停时，关闭一个窗不能承诺世界一定恢复。
- 画面主要按桌面设计：1440×900 主视口，1280×720 可用；406×1000 只做窄屏回退。不能为了窄屏削弱桌面卡面与操作。
- 中文正文 14～16 CSS px、主要操作 16～18、辅助信息通常不低于 12；主按钮点击区域至少 40×40。中文用清晰字体，不把所有字做成低分辨率点阵。
- 世界像素素材最近邻整数缩放；立绘和卡面保留各自比例，不给所有 DOM 文本/原卡图强制像素化。缺图需有占位与可读名称。

## 6. 文件所有权与交付方式

外部模型只能写自己的 `deliverables/playability-v1/PLAY-*/`；正式后端、前端、契约、配置、资源清单、旧交付目录、用户图源与存档只读。不要替其他模型补文件，也不要自动提交、推送、打包或安装成果。

每包包含：

1. `README.md`：启动方法、文件入口、复用的旧成果、仍然存在的局限。
2. `DELIVERY.md`：本轮完成内容、文件清单、素材来源、验证证据、待主模型接入事项；不能把候选写成已上线。
3. `src/`、`preview/`、`fixtures/`：可复用组件或素材源、独立预览、明确的演示输入。
4. `integration.md`：未来接入点、读取的现有字段、缺少的数据、每个操作意图；新字段写“建议”，不改 `contracts/`。
5. `acceptance.md` 与少量截图/短动画：按任务指定关键场景验证；未验证项直接说明，不用几十次相同截图凑数量。

候选页面建议以项目现有服务器下的 `/deliverables/playability-v1/PLAY-*/preview/index.html` 打开；先确认服务器允许访问。若不允许，仅对该候选目录使用独立静态服务，不改正式路由，不发业务请求。

## 7. 合并顺序与验收

1. 用户将 A/B/C 任务书分别交给三个模型。主模型先固定三日进程、统计口径与数据需求，随后实现后端兼容扩展。
2. A 先交四人修复与一个店面代表区域；B 先交采购→收货→上架路径；C 先交 HUD→日报→次日准备路径。小样保留完整文件，便于提前审查，不在阶段一量产全部细节。
3. 主模型审查候选，给各包一次集中的修正清单。继续开发不要求用户反复批准常规细节；明显改变角色外观和重大经营规则再集中呈现。
4. 主模型合并 A 的素材和空间规划，统一实际地图与寻路；合并 B/C 的组件并接入真实 Host，不复制 Mock 成交逻辑。
5. 用隔离新档走完前三日；定向核对旧档载入、交互暂停、日初重读、一次批量交易和一次 NPC 模拟结算。根据触及模块做必要检查，不重复全库验证；正式开赌/完整牌局恢复不包含在本批。
6. 验收：能快速看懂今天做什么；买卖大多无需多层弹窗；卡面可看；顾客行为有原因；店铺升级可见；日报能支持明天决策；钱、卡和任务不会因重试/读档复制。
7. 最终统一提交。私有发布走现有 `npm run publish:private`；不直接推送含原始 vendor 历史的根仓库。EXE 等稳定版本另行处理。
