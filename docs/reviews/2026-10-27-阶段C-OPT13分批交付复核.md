# OPT-13 工作区分批交付复核

日期：2026-10-27（Asia/Shanghai），交付基线 `b981335f`。按 OPT-13 原验收检查热点改善、连续滚动/选择/定价/焦点和生命周期，不增加新的性能达标阈值。

结论：首屏只绘制 120 行确有提速价值，保留实现方向；第一项尚需补修。当前不急于转去查询缓存、存储或全项目拆分，也不要求必须改成固定高度虚拟化。

## 1. 首批底部会同步补齐全量

`collection.mjs` 的 `fillToBottom` 在同一个 rAF 内 while 循环追加，每批之后主动设置 scrollTop 到新的 scrollHeight，下一轮仍满足底部条件，因此会一次绘制所有剩余行。外层虽检查“距底部 600px”，内层仍要求距底部 8px，未真正提前追加。

在独立临时端口和隔离浏览器中，通过真实菜单导入 1,000 张卡，仅作普通滚轮输入，复现结果：

```json
{"kind":"normal-wheel","wheelDelta":240,"before":{"top":7362,"maxTop":7482,"rendered":120,"visible":[104,105,106,107,108,109,110,111,112,113,114,115,116,117,118,119]},"after":{"top":7482,"maxTop":66442,"rendered":1000,"visible":[108,109,110,111,112,113,114,115,116,117,118,119,120,121,122,123]},"unexpectedJump":120}
```

本次没有观察到玩家视口跳至整份列表末尾；确认的问题是单次回调从 120 行同步增加到 1,000 行，而不是逐帧、按需追加下一批。因此不能把这一实现造成的集中绘制当成分批方案无法避免的代价。

修复方向：按帧/时间预算限制单次追加，接近底部预取，保留当前可见卡和滚动位置。快速滚动可持续推进，但不能靠一次 while 填满全列表来满足测试。分批与可测高度的虚拟化均可，选择需有证据。

## 2. 失效的排队回调在筛选后继续执行

`chunkCleanup` 仅 removeEventListener；已经排队的 requestAnimationFrame 没有取消、没有网格代次校验。组件整体 disposed 为 false 时，已被筛选替换的旧闭包仍会执行，向脱离页面的旧网格追加，并写共享 `state.chunkRows`。

同一个真实窗口中，先派发滚动，再立即输入“曹”，下一帧得到：

```json
{"kind":"filter-with-pending-scroll","before":{"oldRows":120,"oldConnected":false,"currentRows":61},"after":{"oldRows":1000,"oldConnected":false,"currentRows":61,"savedChunkRows":1000}}
```

当前只有 61 条筛选结果，脱离页面的旧网格却从 120 填到 1,000，保存草稿也成了 1,000。这是已复现的生命周期缺陷，不能以“关闭组件时会检查 disposed”替代网格重绘的失效处理。

修复要求：每次替换网格、切筛选/排序/页签、更新世界/分支及销毁时取消排队工作，并在回调中验证当前网格身份/代次。增加“滚动回调排队中立即筛选或刷新”的回归，验证旧网格不再追加、新状态不被污染。

## 3. 滚动性能样本的状态混用

`tools/perf/browser.mjs` 在 interactive 阶段滚到了逻辑末行，DOM 已经补齐；随后再次调用 openPanel 复用同一个窗口，再测 scroll。因此保存的 after 样本 `scroll.displayedRows` 是 1,000 / 2,563，与 before 相同。

所以 803→912ms 等数字可以作为“全部行已加载时的滚动样本”，不能证明是批次追加造成的，也不能覆盖第一次滚过首批边界的表现。

后续分开测：

- 新建列表的首批交互；
- 全新首批列表第一次滚动并追加；
- 已加载全部行后的重复滚动；
- 快速跳转、缩放和刷新后的可达性。

明确每个阶段开始时的 DOM 行数和视口位置，使用同环境、同夹具前后对照；不覆写现有原始样本。
