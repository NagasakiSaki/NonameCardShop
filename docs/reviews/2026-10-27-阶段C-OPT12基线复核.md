## 1. NPC 自动开桌并未失效

原报告只检查 `runtime.advance` 中 `tickNpcTables(...,{schedule:false})`，遗漏了随后调用的 `tickMatchQueue(...,{schedule:...})`。

当前正式链路：

```text
runtime.advance
  → tickNpcTables（移动和模拟推进，关闭旧的直接调度）
  → tickMatchQueue
    → 符合条件的 NPC joinQueue
    → 两两配对 registerNpcMatch
    → seatNpcMatch
  → 后续 advance 推进模拟并结算
```

本次使用 `createWorld` + repository 初始记录、正式地图、默认 npcAutoBattles/npcSimulation，仅为两名隔离 NPC 注入各三名不同且已流通武将；不直接调用开桌函数，只循环 `runtime.advance(.25)`。运行结果：

```json
{"node":"v24.15.0","npcAutoBattles":true,"npcSimulation":true,"queueMatched":1,"matches":[{"mode":"kof","simulated":true,"status":"finished","feePaid":20}],"serviceIncome":20}
```

这是功能路径验证，不与作者 Node v22.22.2 的性能数字直接比较。没有操作实际玩家数据。自动 NPC 对局本就是现行规则，无需就“再启用”作新产品决策，也不应开启第二套调度。

## 2. 滚动数据没有测到实际滚动

保存的浏览器证据：

| 实物量 | scrollHeight | clientHeight | finalScrollTop |
| --- | --- | --- | --- |
| 1,000 | 67,150 | 67,150 | 0 |
| 5,000 | 171,938 | 171,938 | 0 |

`browser.mjs` 只在收藏根节点后代寻找滚动容器，未找到时回退到根节点，而真正的窗口滚动体可能是祖先 `.window__body`。此处选到的节点没有滚动范围，所以 62 帧不代表真实千卡滚动流畅；5,000 卡的 1 帧也不能据此归因于前一阶段渲染阻塞。

补测要求：定位实际 overflow 为 auto/scroll 且有范围的滚动体，断言滚动位置和可见行确实变化；在布局完成后开始计量，长任务观察器覆盖打开阶段和滚动阶段，并允许回调交付后再取最终结果。缺少滚动范围、有效夹具或指标支持时明确标记无效/不支持，不能以 0 作为通过。

## 3. 内存提交不等于磁盘提交

`countingRepository` 包装 `memoryRepository`，计时范围是 `inner.commit` 的 structuredClone；`JSON.stringify(next).length` 在计时完成后执行，计算的是 UTF-16 字符数量而非 UTF-8 字节，也不是 IndexedDB/磁盘写入量。序列化测量本身还会增加后续营业步骤的成本。

保留这组数据时应分别命名内存复制耗时、JSON 序列化耗时与估算文本体积；UTF-8 体积用 `Buffer.byteLength`。真实浏览器 IndexedDB 提交需另测事务完成时间、被提交记录范围与故障/并发行为，不能声称测得物理磁盘落盘字节。当前浏览器仓库会把不可变日档拆成独立记录，整记录 JSON 也不等于实际每次写入对象。

因此暂不按“每次写盘 325KB”推导差量/压缩优先级或改动原子提交。

## 4. 营业和牌桌夹具需核实

- `openWorld` 未向 `createRuntime` 传正式地图，无法代表当前有寻路、收银、拆包台和牌桌路线的营业流程。
- `rollDay` 将名为 minutesPerStep 的 30 直接传入接收秒数的 `advance`；默认每秒 2 游戏分钟，因此每步实际前进 60 游戏分钟（还需考虑速度），不能写成 30 分钟一步。
- 受控牌桌原始 `2026-10-27-perf-baseline.json` 中 `registerMs:null`、`settleMs:null`、`matches:0`、`settled:0`，与文档的 3.31ms/0.5ms 不对应。必须确认真实注册及结算至少发生，再给出性能结果。
- 普通和压力场景没有比赛不能证明正式调度失效。需核查在场人数、有效不同武将数、资格、队列、路线、实际购买/拆包/结算计数以及步长；两种场景分别记录输入和业务结果。
- npcPeak 使用全部 NPC 档案数，含离店者和特殊角色，不能直接当作同时在场人数。应区分总档案、在场、购物及比赛人数。

修夹具使用 repository 初始记录是正确做法；构造 clone 后通过真实 `saves.import` 注入也是有效方式。关键在于核对注入后的实际状态和发生的业务，不应机械禁止所有 `inspect()` 快照使用。

## 5. 其他结论边界

- 浏览器首次启动样本混有空世界首次进入和导入后的重载，应拆开冷/热、空档/存量档。Node 独立 buildCatalog 与 createRuntime 是不同测量，后者自身会建目录，不能相加归因浏览器白屏；浏览器瓶颈归因需浏览器分段证据。
- 5,000 张实物在工作区聚合为 2,563 行，1,000 张则为 1,000 行；必须同时记录实物数、不同卡种数与实际显示行数，避免把五倍实物数量当作五倍绘制量。
- 两个规模点不足以定性算法复杂度；目前可表述为这两个夹具的查询/打开耗时变化，下一步通过实现和分段测量定位来源。
- 关闭后 DOM 回落只能说明观察范围内连接节点数恢复，不能证明没有监听器、定时器、离线 DOM 或引用泄漏。原验收要求监听器和长期样本，当前尚未提供。
- 搜索的 fill + 两次 rAF 是自动化端到端等待，尚未核对筛选结果已应用；应记录触发输入、结果匹配和布局可用的终点，避免未来加防抖后假提速。
- CPU 报告的 16 是逻辑处理器数，应使用真实型号和逻辑线程描述，不据此称作 16 个物理核心的桌面 CPU。资源版本、浏览器具体版本和阶段/脚本版本也应入报告。
