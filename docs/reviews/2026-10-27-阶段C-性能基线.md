## 1. 环境与场景

| 项 | 值 |

| 浏览器 | Playwright Chromium，1440×900，`--enable-precise-memory-info` |

**普通与压力分开**：

- 普通（busy-normal）：默认规则 + 1,000 张实物 + 40 个货架包 + 顾客自带牌组；
- 压力（busy-stress）：5,000 张实物 + 200 个货架包 + `npcIntervalMinutes=8` + `npcMatchIntervalMinutes=10`；
- 卡量对比（cards-1000 / cards-5000）只改实物数量，其余同口径。

## 2. Node 侧基线

### 2.1 启动（空世界）

| 阶段 | 耗时 |
| --- | --- |
| 建目录 `buildCatalog`（2,563 卡） | **238 ms** |
| 建运行时 `createRuntime` | **497 ms** |
| 连接 `connect` | 0.56 ms |
| 首个 `shop.snapshot` | 0.64 ms |
| 进程堆 | 102 MB |

启动成本几乎全在“建目录 + 建运行时”，与玩家卡量无关。**这是首次进游戏白屏的主要来源**（浏览器侧首屏中位数 685 ms，见 3.1）。

### 2.2 热查询（p50 / p95，ms）

| 查询 | 空世界 | 1,000 卡 | 5,000 卡 |
| --- | --- | --- | --- |
| `shop.snapshot` | 0.05 / 0.12 | 0.26 / 0.28 | 0.98 / 1.30 |
| `inventory.list`(limit 200) | 0.003 / 0.01 | 0.95 / 3.73 | 5.03 / 7.40 |
| `catalog.list`(limit 200) | 4.48 / 5.13 | 4.50 / 4.84 | 4.57 / 4.88 |
| `market.list` | 0.003 / 0.009 | 0.17 / 0.22 | 1.83 / 3.19 |
| `combat.eligible`(kof) | 0.003 / 0.006 | 4.75 / 6.16 | **31.08 / 33.36** |
| `ledger.daily` | 0.012 / 0.029 | 0.11 / 0.18 | 2.16 / 3.83 |
| `saves.days` | 0.003 / 0.01 | 0.003 / 0.003 | 0.003 / 0.005 |

观察：

1. **`catalog.list` 恒定 ~4.5 ms**，与卡量无关，但它是所有查询里最慢的常量项——每次翻页都重算卡片摘要。
2. **`combat.eligible` 从 4.75 → 31.1 ms（6.5×，卡量 5×）**，超线性；它按武将聚合全部实物并计算三模式评分。
3. `inventory.list`、`market.list`、`ledger.daily` 基本线性，5,000 卡时仍在 2–7 ms。

### 2.3 写盘（每次命令都提交整个世界）

| 指标 | 1,000 卡 |
| --- | --- |
| `commit` p50 / p95 | 2.11 / 3.38 ms |
| 每次提交序列化字节 p50 | **332,953 B（约 325 KB）** |
| 最大一次 | 665,658 B |
| `saves.create` 命令 | 12.9 ms |

结论：单次命令的写盘代价随卡量线性增长，因为提交的是**整个世界**。5,000 卡时约 1.6 MB/次，
每天几十次命令就是几十 MB 的序列化量——这是 `busy-*` 场景里每日耗时的主要组成之一。

### 2.4 跨日与繁忙店铺

| 场景 | 每日 p50 / p95 | 单步（30 分钟）p50 / p95 | 堆 |
| --- | --- | --- | --- |
| `day-rollover`（1,000 卡，无客流推进） | 199 ms（其中 nextDay 67 ms、close 53 ms） | — | — |
| `busy-normal`（1,000 卡，12 NPC，5 天） | **1,053 / 1,384 ms** | 42 / 71 ms | 508 → 474 MB |
| `busy-stress`（5,000 卡，12 NPC，密客流，5 天） | **3,986 / 5,221 ms** | 161 / 278 ms | 657 → 811 MB |

`busy-stress` 的每日耗时是 `busy-normal` 的 3.8 倍，而卡量只增加 5 倍、客流更密——说明
**每步耗时主要由“全量提交 + 每次推进重算”驱动**，不是渲染。

### 2.5 牌桌（受控场景）

`match-settle`（直接调用真实 `tickNpcTables`，schedule:true）：

| 指标 | 值 |
| --- | --- |
| 注册一桌 | 3.31 ms |
| 结算一步 | 0.5 ms |
| 单次 tick p50 / p95 | 0.001 / 0.039 ms |

**重要发现（需产品决策，本轮未改）**：`runtime.advance` 调用 `tickNpcTables` 时固定
`{schedule:false}`（`modules/backend/runtime.mjs:375`），而 `nextNpcMatchAt` 只在 `schedule` 分支里写。
也就是说**正式运行时不会自动开 NPC 牌桌**，该能力目前只在测试里被驱动（`tests/three-formats.mjs`、
`tests/npc-day-loop.mjs`、本基线受控场景）。是否启用属于玩法/营收决策，本轮只记录，不擅自打开。

## 3. 浏览器侧基线（正式入口 `/?profile=legacy`）

### 3.1 首屏

| 指标 | 1,000 卡 | 5,000 卡 |
| --- | --- | --- |
| 首屏就绪中位数（3 次） | 685 ms | 695 ms |
| 初始 DOM 节点 | 85 | 85 |
| 首屏堆 | 202 MB | 73 MB |

首屏与卡量无关（与 2.1 一致），主要是目录构建与场景初始化。

### 3.2 反复开关交易工作区

| 指标 | 1,000 卡（8 次） | 5,000 卡（6 次） |
| --- | --- | --- |
| 打开 p50 | **478 ms** | **2,345 ms** |
| 关闭 p50 | 32 ms | 41 ms |
| 打开时 DOM | 12,212 | **30,967** |
| 关闭后 DOM | 129 | 129 |
| 残留窗口栈 | 无 | 无 |

**这是本轮最明显的热点**：打开窗口会把全部行一次性渲染进 DOM，1,000 行≈1.2 万节点、
5,000 行≈3.1 万节点，耗时随行数超线性增长（478 → 2,345 ms）。关闭后 DOM 回落到 129，
说明没有节点泄漏，问题在**一次性渲染**而不是泄漏。

### 3.3 千卡滚动与长任务

| 指标 | 1,000 卡 |
| --- | --- |
| 1 秒内 rAF 帧数 | 62 |
| 长任务数量 / 总时长 | 0 / 0 ms |

5,000 卡时该场景只记录到 1 帧——因为窗口刚渲染完 3 万节点，主线程仍在忙，属于**测量被前一步阻塞**，
不是滚动本身掉帧。滚动本身（1,000 卡）是满帧且无长任务。

### 3.4 搜索输入

| 指标 | 1,000 卡 | 5,000 卡 |
| --- | --- | --- |
| 输入到列表更新 p50 / p95 | 56 / 74 ms | 65 / 82 ms |
| 焦点是否保持 | 是 | 是 |
| 清空后行数 | 1,000 | 2,563（按卡种聚合） |

搜索延迟主要来自“过滤后整表重绘”，与卡量弱相关（分组后行数被压到 2,563 上限）。

## 4. 候选优化（按证据排序，尚未实施）

| 优先级 | 候选 | 依据 | 风险 |
| --- | --- | --- | --- |
| 1 | 交易工作区分批/虚拟渲染（保留连续滚动与全部行可达） | 打开 478→2,345 ms、DOM 1.2→3.1 万 | 行复用不能串卡、选中与定价必须绑定 inventoryRef；需保留滚动/焦点/右键 |
| 2 | `combat.eligible` 按武将预聚合（而不是每次扫全部实物） | 5,000 卡 31 ms，是选将面板的主要延迟 | 需说明缓存归属/键/失效；锁与保护状态变化要失效 |
| 3 | 写盘从“整世界提交”改为差量或压缩（先测量再定） | 每次命令 325 KB @1,000 卡 | 不能跳过持久化或延后真实扣款；必须保持事务原子 |
| 4 | `catalog.list` 摘要缓存 | 恒定 4.5 ms，翻页重复计算 | 目录是只读的，缓存风险低 |
| 5 | 搜索输入防抖（当前 56 ms/键，尚未影响可用性） | 3.4 | 不能牺牲焦点与即时反馈 |

**不做**：不引入新库、不切 Phaser 渲染器、不把持久化改成异步延后——这些都需要更强的证据。

## 5. 未覆盖

1. 未测真实安装版 EXE（未重打包），只有 Chromium。
2. 未测 60 FPS 长时间（>10 分钟）运行的帧时间分布与内存曲线；只测了 1 秒滚动与 5–8 次窗口开关。
3. `busy-*` 场景的 NPC 牌桌没有发生（见 2.5 的调度发现），牌桌负载只有受控单桌数据。
4. 未测多标签/多存档同时打开、未测低端机（本轮硬件为 16 核桌面 CPU）。
5. 未测剧情/对话、选将面板、拆包动画等其它重绘路径。
6. 5,000 卡的滚动数据被前一步渲染阻塞，需要单独在“已渲染完成”的状态下重测。
