## 滚动补测

`tools/perf/browser.mjs` 先测 interactive 的逻辑末行，再在同一个已加载全量的窗口统一回到顶部，断言开始/结束 DOM 行数均等于逻辑总数；之后才为首次追加独立 reload。新增 `--render-mode full|batched`：full 仅在临时服务响应中把首批上限改为全量，不修改正式组件，作为当前实现的全量绘制对照，**不是历史版本复现**。报告 v4 包含原文件、实际响应及输入资源 hash；原始旧证据保留。

同机 Node v24.15.0、Chromium 156.0.8078.4、1440×900，四份 `perf-scroll-v4-{full,batched}-{1000,5000}.json`：

| 指标 | 1,000 行 full → batched | 2,563 行 full → batched |
| --- | --- | --- |
| 首批点击终点 | 262 → 49 ms | 495 → 152 ms |
| 末行点击累计终点 | 982 → 1,112 ms | 3,057 → 2,614 ms |
| 打开 p50（3 次） | 736 → 89 ms | 2,400 → 190 ms |
| 全量重复滚动开始行数 | 1,000 → 1,000 | 2,563 → 2,563 |
| 全量重复滚动开始位置 | 0 → 0 | 0 → 0 |
| rAF 数 / 实测时间 | 12/约1.2秒 → 29/约1.2秒 | 5/约1.9秒 → 10/约1.2秒 |
| 长任务总时长 | 1,027 → 599 ms | 1,934 → 1,161 ms |

这些是短时诊断样本，不是自然游玩帧率保证。全量滚动仍有长任务，末行 1,000 行仍略慢；首屏改善不等于所有性能问题解决。新脚本中 `scrollHeight` 等几何读取仍可能触发布局，不将它描述为完全无强制布局。

## 选将查询

`matches.eligible` 改为单次调用内复用同一卡种的角色评分元信息，收藏使用 Set，稳定地先输出收藏再输出其他副本。每张实物仍独立判断 owner、位置、锁/保护、流通、技能兼容；每份角色评分结果仍是独立对象。没有跨查询或跨世界缓存，也不需要新增失效协议。

工具 `npm run perf:eligible` 在隔离内存仓库中生成 1,000/5,000 副本夹具，核对实际数量；保留完整 DTO hash。`eligibility-reference.mjs` 是从接手提交提取的只读对照函数，仅用于测试/测量，不被运行时引用。同进程交替旧/新函数，避免把不同进程的冷/热差异当成收益。

`eligible-paired.json`（30 次预热后样本）：

| 副本 / 卡种 | 旧函数 p50 → 新函数 p50 | 返回 DTO 克隆 p50（旧/新结构） |
| --- | --- | --- |
| 1,000 / 1,000 | 1.086 → 1.046 ms | 2.993 / 2.908 ms |
| 5,000 / 2,563 | 8.539 → 6.282 ms | 15.270 / 14.175 ms |
| 5,000 / 20 | 4.245 → 2.288 ms | 11.707 / 11.240 ms |

独立进程 Host 基线和初次 after 数据也保留，初次 after 的 1,000 副本 Host 反而更慢；因此不宣称整个 Host 或选将界面提速某一百分比。同进程样本只能支持减少纯查询的重复工作，主要剩余成本是 DTO 克隆。三个夹具的新旧结果 hash 均一致，不靠跳过克隆、资格或持久化提速。

本轮检查：`tests/eligibility-query.mjs` 验证精确旧 DTO、重复副本角色分不共享可变对象、后续锁/保护/收藏/流通/配置即时变化及三赛制；`contract-samples`、`three-formats` 同时通过。新增检查进入默认 backend。最后跨结构回归另行记录。
