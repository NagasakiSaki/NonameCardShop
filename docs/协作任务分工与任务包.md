## 2. 如何判断是否适合交给较轻量模型

适合分出去：输入明确、文件范围小、结果能机械验收、失败不会影响资金/存档的任务，例如清单、纯展示组件、CLI 参数封装、固定流程截图。

由主模型负责：需要同时理解多模块不变量、数据迁移、异常恢复或长期经济反馈的任务。模型名称不能替代验收；zcode / WorkBuddy 的实际能力和访问方式尚未在本工程验证，下面只按任务性质安排候选执行者。

| 工作 | 判断 | 建议承担方 | 完成标准 / 边界 |
| --- | --- | --- | --- |
| 素材路径、尺寸、引用和署名清单 | 规则明确，可立即分出 | WorkBuddy 或 zcode | 输出缺失项报告；不删除、不修规则 |
| 人物工具的 validate / list-parts / contact-sheet 包装 | 规则明确，可立即分出 | zcode | 包装现有纯函数；不改像素渲染核心 |
| 卡片/商品纯展示组件样稿 | 可分出，先只用 Mock | zcode 或 WorkBuddy | 独立页面可看卡面、数量、价格、稀有度；不调用真实交易 |
| 固定尺寸截图与可复现问题报告 | 规则明确，可立即分出 | WorkBuddy | 指定路线、视口、错误、截图；使用隔离数据 |
| 资料表整理、文档链接核对 | 可分出 | 两者均可 | 保留来源，不自创译名，不把规划写成实现 |
| 前端整体信息架构、关键操作路径 | 需要判断，主模型先定 | 主模型 + 用户试玩 | 比旧版更易采购/看卡/售卡，减少层层弹窗 |
| v2 DTO、ArtRef、旧版适配和错误语义 | 高耦合 | 主模型 | 冻结字段、权威来源和版本兼容后再分页面 |
| 批量报价/扣款/收货原子性、重复点击幂等 | 高耦合 | 主模型 | 过期报价、重复请求、读档后引用均有明确处理 |
| 实物卡归属、可售数量、参赛/收藏锁定 | 高耦合 | 主模型 | 不复制实物、不负库存、不误卖保留牌 |
| 评分、稀有度、盒配额、进售价格反馈 | 设计与数值联动 | 主模型 | 全局分级不因卡包变化；核对期望卡值及经营收益 |
| 存档迁移、牌局恢复、下注与抽水 | 高风险状态联动 | 主模型 | 先保证恢复/结算一致，再开放下注 |
| 角色像不像、服饰与发型是否好看 | 主观验收 | 主模型审查，用户最终取舍 | 可分出变体制作，不能仅靠“测试通过”定稿 |
| 最终合并、入口切换、Git 私有发布 | 单一负责人 | 主模型 | 审查差异后合并；exe 等稳定后另议 |

## 4. 主模型随后推进的顺序

1. 收尾本轮人物修复：核对记录、工具说明、预览、提交和私有发布。
2. 冻结最小交易展示数据和 UI-01 样稿输入；不先扩写所有页面。UI-01 的演示字段只在 Mock 内有效。
3. 审查 UI-01 的卡面密度、操作次数和采购信息，选定卡面详情、供应商购物篮、单卡市场三条路径。
4. 实现权威报价与批量命令、兼容适配，再把已验收的展示组件接入 Host。
5. 接入收货、拆包/拆盒、重复牌批量上架、日结和管理页；交互暂停统一归口。
6. 完成完整牌局恢复和结算边界后，再推进店内下注/抽水。最后切换入口；稳定前不重建 exe。

这份清单是后续工作安排，不表示本轮会把所有步骤一次实现。人物工作和任务拆分完成后，前端实施应按上述依赖逐步推进。

## 5. 多工具协作规则

- 开始先记录 `git rev-parse HEAD`、`git status --short`，只读取和修改任务许可的路径。不要运行 `git reset --hard`、`git clean` 或全目录格式化。
- 推荐独立分支/独立工作副本；若共享当前目录，同一文件只能有一个写入者。未知的已有改动属于其他工作，不能覆盖。
- 本轮已有其他改动的 `docs/美术与前端独立开发交接文档.md` 不归这些任务修改。
- 禁止修改 `modules/backend/`、经营数据/评分、存档、引擎 vendor、正式入口和 `assets/frontend/manifest.json`，除非主模型重新明确分配。
- 不把官方参考图、私人存档、浏览器资料、凭据或整个 `.local/` 提交/上传。无 API 密钥需求，不购买或安装付费服务。
- 不让外部工具自行提交到 GitHub或发布 exe；由主模型审查后统一提交，私有发布使用 `npm run publish:private`。
- 每项只跑相关验收一次；失败定位原因后再跑。不要反复跑全套引擎/经济测试或删失败测试。
- 返回变更文件列表、基线、实现/未实现项、相关命令及结果、截图路径和已知问题。无法执行的部分明确标记，禁止写“已完成”掩盖。
